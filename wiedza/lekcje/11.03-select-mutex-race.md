# Lekcja 11.3 — `select`, `Mutex`, wyścigi

## Cel
Po lekcji uczeń:
- Czeka na kilka kanałów naraz przez `select`
- Dodaje limit czasu przez `time.After`
- Rozumie, czym jest wyścig danych, i wykrywa go przez `-race`
- Chroni wspólne dane przez `sync.Mutex`

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Czekasz na kuriera i na telefon od lekarza. Nie wiesz, co przyjdzie pierwsze. Jak czekasz na oba naraz?"

**Drugie pytanie:**
> "A gdy czekasz na telefon, który może nigdy nie przyjść — do kiedy czekasz?"

→ do jakiejś godziny. Potem robisz coś innego. To jest limit czasu (timeout).

**Trzecie:**
> "Dwie osoby jednocześnie wpisują ostatnią cyfrę do tego samego formularza na papierze. Co wyjdzie?"

## Krok 2 — Mostek (10 min)
**Mostek:**
> "`select` to czekanie na kilka kanałów naraz — wygrywa ten, który pierwszy będzie gotowy."

Uczeń tworzy `kurs/zadania/32-select/main.go`:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	kurier := make(chan string)
	lekarz := make(chan string)

	go func() {
		time.Sleep(300 * time.Millisecond)
		kurier <- "paczka"
	}()
	go func() {
		time.Sleep(500 * time.Millisecond)
		lekarz <- "wyniki"
	}()

	for range 2 {
		select {
		case p := <-kurier:
			fmt.Println("przyszedł kurier:", p)
		case w := <-lekarz:
			fmt.Println("dzwonił lekarz:", w)
		}
	}
}
```

**Pytania:**
- "Który przyszedł pierwszy? Zamień czasy `Sleep` i sprawdź ponownie."
- "Porównaj z `switch` z lekcji 3.2 — co jest podobne, co inne?" → wygląd; ale `select` **czeka**, a gałęzie to operacje na kanałach
- "Czemu pętla `for range 2`? Co się stanie bez niej?" → `select` obsłuży tylko jedno zdarzenie

## Krok 3 — Eksperyment (15-20 min)

1. **Limit czasu:**
   ```go
   select {
   case p := <-kurier:
       fmt.Println("mam:", p)
   case <-time.After(100 * time.Millisecond):
       fmt.Println("nie doczekałem się, idę dalej")
   }
   ```
   > "`time.After` zwraca kanał, do którego coś wpadnie po zadanym czasie. Do czego przyda ci się limit czasu w prawdziwym programie?" → sieć, która nie odpowiada
2. **`default` — nie czekaj wcale:**
   ```go
   select {
   case p := <-kurier:
       fmt.Println("mam:", p)
   default:
       fmt.Println("nic nie ma, robię swoje")
   }
   ```
   > "Z `default` `select` nigdy nie blokuje. Kiedy to dobre, a kiedy prowadzi do bezsensownego kręcenia się w kółko?"
3. **Wyścig danych** — kluczowy eksperyment:
   ```go
   var licznik int
   var wg sync.WaitGroup

   for range 1000 {
       wg.Add(1)
       go func() {
           defer wg.Done()
           licznik++
       }()
   }
   wg.Wait()
   fmt.Println(licznik)
   ```
   > "Ile powinno wyjść? Uruchom pięć razy."
   → za każdym razem inna liczba, prawie nigdy 1000
   > "Czemu? `licznik++` wygląda jak jedna operacja."
   → to trzy: odczytaj, dodaj, zapisz. Dwie goroutine mogą odczytać tę samą wartość i zapisać ten sam wynik.
4. **Wykrywacz wyścigów:**
   ```sh
   go run -race ./32-select
   ```
   → `WARNING: DATA RACE` z dokładnymi liniami zapisu i odczytu
   > "To najlepsze narzędzie diagnostyczne w Go. Kiedy je uruchamiać?" → zawsze, gdy program ma współbieżność. Także `go test -race`.
5. **`sync.Mutex` — zamek:**
   ```go
   var (
       licznik int
       mu      sync.Mutex
       wg      sync.WaitGroup
   )

   for range 1000 {
       wg.Add(1)
       go func() {
           defer wg.Done()
           mu.Lock()
           licznik++
           mu.Unlock()
       }()
   }
   wg.Wait()
   fmt.Println(licznik)      // zawsze 1000
   ```
   > "Co robi `Lock`?" → wpuszcza tylko jedną goroutine naraz; reszta czeka
   > "Uruchom z `-race`. Cisza?"
   > "Czemu `Unlock` tuż po, a nie na końcu funkcji?" → im krócej trzymasz zamek, tym mniej innych czeka
6. **Zamek w strukturze** — typowy wzorzec:
   ```go
   type BezpiecznyLicznik struct {
       mu sync.Mutex
       n  int
   }

   func (b *BezpiecznyLicznik) Zwieksz() {
       b.mu.Lock()
       defer b.mu.Unlock()
       b.n++
   }

   func (b *BezpiecznyLicznik) Wartosc() int {
       b.mu.Lock()
       defer b.mu.Unlock()
       return b.n
   }
   ```
   > "Czemu odbiornik `*BezpiecznyLicznik`, nie wartościowy?" → z 7.2: kopiowanie zamka psuje jego działanie. **Struktury z `Mutex` przekazuj zawsze przez wskaźnik.**

## Krok 4 — Pogłębienie (10 min)

**Kanał czy mutex?**
| Sytuacja | Narzędzie |
| --- | --- |
| Przekazanie danych między goroutine | kanał |
| Ochrona wspólnego stanu (licznik, mapa, cache) | mutex |
| Czekanie na kilka źródeł | `select` |
| Poczekanie na zakończenie | `WaitGroup` |

> "Motto Go mówi 'komunikuj się przez kanały', ale mutex bywa prostszy. Reguła praktyczna: **dane w ruchu → kanał; stan w miejscu → mutex.**"

**Mapa nie jest bezpieczna współbieżnie:**
```go
m := map[string]int{}
// dwie goroutine piszące jednocześnie → fatal error: concurrent map writes
```
> "Go wykrywa to i **zabija program** — nawet bez `-race`. Ratunek: mutex albo `sync.Map`."

**`RWMutex`** — gdy odczytów jest dużo więcej niż zapisów:
```go
var mu sync.RWMutex
mu.RLock()   // wielu czytających naraz
mu.RUnlock()
mu.Lock()    // jeden piszący, wyłącznie
mu.Unlock()
```

**Zakleszczenie przy zamkach:** goroutine A trzyma zamek 1 i chce 2, B trzyma 2 i chce 1 → obie stoją. Zasada: **zawsze zajmuj zamki w tej samej kolejności**, a najlepiej używaj jednego.

**`defer mu.Unlock()`** — najbezpieczniejszy zapis: zamek zostanie zwolniony nawet przy panice. Cena: trzymasz go do końca funkcji.

## Pułapki
- **Zapomniany `Unlock`** → wszystkie pozostałe goroutine stoją na zawsze. `defer` to rozwiązuje.
- **Kopiowanie struktury z `Mutex`** → `go vet` ostrzega (`passes lock by value`). Zawsze wskaźnik.
- **`select` bez `default` i bez gotowego kanału** → blokuje. Czasem o to chodzi, czasem nie.
- **`select` w pętli z `default`** bez żadnego czekania → program zżera procesor.
- **Zamek trzymany zbyt długo** — cała współbieżność zamienia się w kolejkę.
- **Poleganie na `-race` jako dowodzie** — wykrywacz widzi tylko to, co faktycznie się wykonało. Brak ostrzeżenia nie jest gwarancją.
- **Wyścig, który "prawie nigdy" się nie zdarza** — pojawi się na cudzym komputerze, w produkcji, o trzeciej w nocy. Dlatego `-race` używa się zawsze przy testach kodu współbieżnego.
