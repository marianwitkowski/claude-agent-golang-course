# Lekcja 10.3 — Narzędzia i debugowanie

## Cel
Po lekcji uczeń:
- Używa `go vet` i rozumie, czym różni się od kompilatora
- Debuguje metodycznie: hipoteza → sprawdzenie → wniosek
- Zna `delve` jako opcję i wie, kiedy wypisywanie wystarcza
- Wie o `go fix` jako narzędziu modernizacji kodu

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Program się kompiluje, uruchamia i daje **zły wynik**. Od czego zaczynasz szukanie?"

**Co chcesz usłyszeć:** zwykle "wypisuję różne rzeczy w środku" — i to jest dobra odpowiedź.

**Drugie pytanie:**
> "Zgubiłeś klucze w mieszkaniu. Sprawdzasz wszystkie miejsca po kolei, czy zastanawiasz się najpierw, gdzie byłeś ostatnio z kluczami w ręce?"

→ debugowanie to zawężanie obszaru poszukiwań, nie przeszukiwanie wszystkiego.

## Krok 2 — Mostek (5-10 min)
**Mostek:**
> "Masz trzy poziomy pomocy. Kompilator łapie to, co niepoprawne. `go vet` łapie to, co poprawne, ale podejrzane. Resztę musisz znaleźć sam — i do tego jest metoda."

Uczeń tworzy `kurs/zadania/29-narzedzia/main.go` z celowymi błędami:

```go
package main

import "fmt"

type Punkt struct{ X, Y int }

func main() {
	p := Punkt{1, 2}
	fmt.Printf("%d\n", "tekst")     // zły czasownik
	fmt.Printf("%d %d\n", p.X)      // brakuje argumentu
	fmt.Println(p)
}
```

```sh
go build ./29-narzedzia     # przechodzi (albo tylko ostrzega)
go vet ./29-narzedzia       # łapie oba
```

**Pytania:**
- "Co powiedział `go vet`, czego nie powiedział kompilator?"
- "Czemu kompilator to przepuszcza?" → składnia i typy są w porządku; problem jest w **sensie**, nie w formie
- "Kiedy `go vet` uruchamia się sam?" → przy `go test` (z 10.1)

## Krok 3 — Eksperyment (15 min)

1. **Co jeszcze łapie `go vet`:**
   ```go
   // zgubiony wynik
   var s []int
   append(s, 1)                       // vet: result of append is not used

   // nieosiągalny kod
   func f() int { return 1; fmt.Println("nigdy") }

   // porównanie, które zawsze daje ten sam wynik
   var x uint = 5
   if x >= 0 { }                      // vet: always true
   ```
   > "Wszystkie się kompilują. Wszystkie są prawie na pewno błędem."
2. **Metoda debugowania — na prawdziwym przykładzie.** Uczeń pisze kod z ukrytym błędem:
   ```go
   func srednia(l []int) float64 {
       suma := 0
       for i := 1; i < len(l); i++ {     // błąd: zaczyna od 1
           suma += l[i]
       }
       return float64(suma) / float64(len(l))
   }

   func main() {
       fmt.Println(srednia([]int{2, 4, 6}))   // 3.33 zamiast 4
   }
   ```
   Prowadź ucznia metodą, nie podpowiedzią:
   - "Jakiego wyniku się spodziewasz? Policz na kartce." → 4
   - "Co dostajesz?" → 3.33
   - "Wypisz `suma` i `len(l)` przed zwróceniem. Które z nich jest złe?"
   - "Skoro suma to 10 zamiast 12 — czego brakuje?"
   - "Wypisz `i` i `l[i]` w każdym obiegu. Ile obiegów było?"
   > **To jest ta metoda:** sprawdzasz, gdzie przewidywanie rozjeżdża się z rzeczywistością, i zawężasz.
3. **Wypisywanie do diagnostyki** — narzędzia, które uczeń ma:
   ```go
   fmt.Printf("%+v\n", struktura)     // pola z nazwami (7.1)
   fmt.Printf("%#v\n", struktura)     // zapis jak w kodzie Go
   fmt.Printf("%T\n", zmienna)        // typ (2.3)
   log.Printf("po pętli: suma=%d", suma)   // z czasem, na wyjście błędów (6.3)
   ```
   > "`%#v` na slice struktur — spróbuj. Co pokazuje więcej niż `%v`?"
4. **Debugger `delve`** — uczeń instaluje i próbuje:
   ```sh
   go install github.com/go-delve/delve/cmd/dlv@latest
   dlv debug ./29-narzedzia
   ```
   Podstawowe komendy: `break main.srednia`, `continue`, `next`, `print suma`, `quit`.
   > "Kiedy debugger jest wart zachodu, a kiedy dwie linie `Printf` są szybsze?"
   → debugger wygrywa przy skomplikowanym stanie i wielu zmiennych; przy prostym błędzie wypisanie jest szybsze
   W VS Code z rozszerzeniem Go debugger działa graficznie (F5), bez komend.
5. **`go fix` — modernizacja:**
   ```sh
   go fix ./...
   ```
   > "Uruchom na swoim starym kodzie z modułu 4. Co proponuje?" (np. `sort.Ints` → `slices.Sort`)

## Krok 4 — Pogłębienie (10 min)

**Trzy poziomy kontroli — podsumowanie:**
| Narzędzie | Co łapie | Kiedy uruchamiać |
| --- | --- | --- |
| kompilator (`go build`) | błędy składni i typów | zawsze, automatycznie |
| `gofmt` | formatowanie | przy zapisie w edytorze |
| `go vet` | podejrzane, ale poprawne konstrukcje | przed każdym commitem |
| `go test` | błędy logiki | przy każdej zmianie |
| `go test -race` | wyścigi (moduł 11) | gdy jest współbieżność |

**Metoda debugowania — do zapamiętania:**
1. **Odtwórz** — najmniejszy przypadek, który psuje. Bez tego szukasz po omacku.
2. **Przewiduj** — powiedz na głos, co powinno wyjść w danym miejscu.
3. **Sprawdź** — wypisz i porównaj z przewidywaniem.
4. **Zawężaj** — połowa kodu działa? Szukaj w drugiej.
5. **Napraw jedną rzecz** — potem sprawdź ponownie.
6. **Napisz test** (10.1), żeby ten błąd nie wrócił.

**Częste błędy i gdzie ich szukać** — ściąga dla ucznia:
| Objaw | Najczęstsza przyczyna | Lekcja |
| --- | --- | --- |
| `index out of range` | pętla do `<=` zamiast `<` | 4.1 |
| `nil pointer dereference` | użycie wyniku bez sprawdzenia `err` | 7.2, 6.1 |
| pętla nie zmienia slice'a | `range` daje kopię | 4.4 |
| metoda nie zmienia struktury | odbiornik wartościowy | 7.2 |
| dziwny wynik dzielenia | dzielenie całkowite | 2.2 |
| pole znika w JSON | mała litera w nazwie pola | 9.2 |
| plik pusty po zapisie | brak `Flush()` / `Close()` | 9.1 |
| `errors.Is` nie działa | `%v` zamiast `%w` | 6.2 |

> "Zapisz to sobie. Osiem najczęstszych błędów w Go i wszystkie już widziałeś."

**Linter `golangci-lint`** — poza biblioteką standardową, ale popularny: zbiera kilkadziesiąt kontroli w jednym narzędziu. Wzmianka, nie instalacja.

## Pułapki
- **Bezmyślne wypisywanie** — dziesięć `Println` bez hipotezy daje ścianę tekstu i żadnej odpowiedzi. Najpierw przewidywanie, potem sprawdzenie.
- **Naprawianie kilku rzeczy naraz** — nie wiadomo, która pomogła (a która zepsuła coś innego).
- **Zostawione `Println` diagnostyczne** — w gotowym programie zaśmiecają wyjście. Do diagnostyki: `log` (6.3).
- **Ignorowanie `go vet`** — to darmowe wykrycie realnych błędów.
- **Debugger zamiast myślenia** — krokowanie przez 200 linii bez hipotezy trwa dłużej niż jedno dobre pytanie.
- **"To działało wczoraj"** — sprawdź `git diff` (jeśli uczeń już używa gita) albo przypomnij sobie, co zmieniałeś.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`go fix ./...`** (przebudowane w 1.26) — modernizatory: automatyczna zamiana starych idiomów na nowe. Doskonałe narzędzie dydaktyczne.
- **`go doc -http :8080`** (1.25) — dokumentacja lokalnie w przeglądarce.
- **`go version -m -json binarka`** (1.25) — informacje o zbudowanym programie w formacie JSON.
- **`stdversion`** w `go vet` (domyślnie od 1.27) — ostrzega, gdy używasz funkcji nowszej niż wersja z `go.mod`. Bardzo przydatne, gdy uczeń kopiuje kod z internetu.

## Notatki tutora
- **Metoda z kroku 4 jest ważniejsza niż wszystkie narzędzia razem wzięte.** Uczeń, który umie zawężać obszar poszukiwań, poradzi sobie w każdym języku.
- **Tabela częstych błędów to najbardziej praktyczna rzecz w tej lekcji.** Warto, żeby uczeń zapisał ją w `kurs/lekcje/`.
- **Nie zmuszaj do `delve`.** Wielu doświadczonych programistów Go debuguje wypisywaniem. Pokaż, że istnieje, i idź dalej.
- Eksperyment 2 prowadź **wyłącznie pytaniami**. To najlepsze miejsce w kursie na czysto sokratejskie prowadzenie — uczeń ma cały aparat, żeby znaleźć błąd sam.
- Jeśli uczeń nie zna gita, a zbliża się moduł 12 — dobry moment, żeby wspomnieć, że w 12.3 będzie o zapisywaniu wersji projektu.
