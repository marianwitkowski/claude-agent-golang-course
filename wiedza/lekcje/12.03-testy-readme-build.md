# Lekcja 12.3 — Testy, dokumentacja, budowanie

## Cel
Po lekcji uczeń:
- Ma testy pokrywające główne ścieżki swojego projektu
- Napisał README, z którego obca osoba zrozumie, jak używać programu
- Zbudował binarkę i uruchomił ją poza katalogiem projektu
- Zbudował wersję na inny system operacyjny

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Twój program działa. Wysyłasz go koledze. Co musi dostać oprócz pliku, żeby z niego skorzystał?"

**Drugie pytanie:**
> "Za pół roku wracasz do tego kodu, żeby dodać funkcję. Co chciałbyś wtedy zastać?"

→ opis, jak to uruchomić, i testy mówiące, czy coś zepsułeś.

## Krok 2 — Mostek (5-10 min)
**Mostek:**
> "Różnica między 'kodem, który działa' a 'programem' to trzy rzeczy: testy, opis i plik, który da się uruchomić bez Go."

**Plan tej lekcji:** testy → README → build.

## Krok 3 — Eksperyment (20-25 min)

**A. Testy do projektu** (15 min)

Uczeń wybiera trzy funkcje ze swojego projektu i pisze do nich testy — najlepiej te, w których:
- jest jakieś liczenie albo przekształcenie danych
- jest obsługa błędnych danych
- pojawiały się już błędy

```go
func TestDodajZadanie(t *testing.T) {
	var lista []Zadanie
	lista = dodaj(lista, "kupić mleko")

	if len(lista) != 1 {
		t.Fatalf("len = %d, oczekiwano 1", len(lista))
	}
	if lista[0].Tresc != "kupić mleko" {
		t.Errorf("tresc = %q, oczekiwano %q", lista[0].Tresc, "kupić mleko")
	}
}
```

Test operacji na pliku — z `t.TempDir()` (10.1):
```go
func TestZapisOdczyt(t *testing.T) {
	sciezka := filepath.Join(t.TempDir(), "zadania.json")

	oryginal := []Zadanie{{ID: 1, Tresc: "test"}}
	if err := zapisz(sciezka, oryginal); err != nil {
		t.Fatalf("zapis: %v", err)
	}

	wczytane, err := wczytaj(sciezka)
	if err != nil {
		t.Fatalf("odczyt: %v", err)
	}
	if len(wczytane) != 1 || wczytane[0].Tresc != "test" {
		t.Errorf("wczytane = %+v", wczytane)
	}
}
```

Uczeń uruchamia:
```sh
go test ./...
go test -cover ./...
go vet ./...
gofmt -l .
```
> "Cztery komendy przed każdym uznaniem czegoś za skończone. Cisza znaczy: w porządku."

**Test przypadku, który kiedyś nie działał:**
> "Przypomnij sobie błąd, który cię zablokował w trakcie pisania. Napisz test, który by go złapał."
→ to najcenniejszy test w całym projekcie.

**B. README** (10 min)

Uczeń pisze `README.md` — minimalny szkielet:
```markdown
# zadania

Prosty menedżer zadań w wierszu poleceń. Przechowuje zadania w pliku JSON.

## Instalacja

    go build -o zadania .

## Użycie

    zadania dodaj "kupić mleko"
    zadania lista
    zadania zrobione 1

## Opcje

    -plik ścieżka do pliku z danymi (domyślnie: zadania.json)

## Wymagania

Go 1.22 lub nowszy.
```

**Pytania:**
- "Wyobraź sobie, że to nie ty. Czy z tego opisu wiesz, co program robi i jak go uruchomić?"
- "Czego brakuje?" → najczęściej: przykładu wyniku i informacji, gdzie trzymane są dane

**C. Budowanie** (10 min)

```sh
go build -o zadania .
./zadania lista
ls -lh zadania
```
> "Ile waży? Co jest w środku?" → cały program plus wszystko, czego potrzebuje. Dlatego działa bez instalowania Go.

Uruchomienie z innego katalogu:
```sh
cd ~ && ~/Projects/.../zadania lista
```
> "Zadziałało? Gdzie program szukał pliku z danymi?"
→ w bieżącym katalogu. **Częsty problem:** program działa "w projekcie", a nie działa uruchomiony skądinąd. Rozwiązanie: opcja `-plik` albo katalog domowy użytkownika (`os.UserHomeDir()`).

**Kompilacja na inny system** — jedna komenda:
```sh
GOOS=windows GOARCH=amd64 go build -o zadania.exe .
GOOS=linux   GOARCH=arm64 go build -o zadania-linux-arm64 .
file zadania.exe
```
> "Zbudowałeś program na Windows z macOS-a, bez żadnych dodatkowych narzędzi. To jedna z rzeczy, za które ludzie lubią Go."

**Mniejsza binarka:**
```sh
go build -ldflags="-s -w" -o zadania .
```
> "Usuwa informacje diagnostyczne. Program mniejszy, ale trudniej go debugować."

Po eksperymentach uczeń kasuje binarki (są w `.gitignore`).

## Krok 4 — Pogłębienie (10 min)

**`go install` — program dostępny wszędzie:**
```sh
go install .
zadania lista        # działa z każdego katalogu
```
> "Trafia do `$(go env GOPATH)/bin`. Jeśli komenda nie działa, ten katalog nie jest w `PATH`."

**Wersja w programie** — miła rzecz, którą warto mieć:
```go
var wersja = "dev"

func main() {
	if *pokazWersje {
		fmt.Println("zadania", wersja)
		return
	}
}
```
```sh
go build -ldflags="-X main.wersja=1.0.0" -o zadania .
```

**Git — jeśli uczeń jeszcze nie używa:**
```sh
git init
git add .
git commit -m "pierwsza działająca wersja"
```
> "Od teraz możesz eksperymentować bez strachu — zawsze wrócisz do działającej wersji."
Podstawy do przekazania: `git status`, `git add`, `git commit`, `git log`, `git diff`. Nic więcej na tym etapie.
`.gitignore` dla projektu Go: binarki, pliki danych, `*.exe`.

**Lista kontrolna "projekt skończony":**
- [ ] `go test ./...` przechodzi
- [ ] `go vet ./...` milczy
- [ ] `gofmt -l .` milczy
- [ ] README pozwala obcej osobie uruchomić program
- [ ] program działa uruchomiony spoza katalogu projektu
- [ ] sensowny komunikat przy błędnych argumentach
- [ ] binarka zbudowana i sprawdzona

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`, ale zwykle: dokończenie listy kontrolnej. Dodatkowo:
- 🔥 Napisz README i daj komuś do przeczytania (albo przeczytaj po dniu przerwy)
- ⭐ Dopisz testy do trzech funkcji; sprawdź pokrycie przed i po
- ⚡ Zbuduj wersje na trzy systemy, dodaj opcję `-wersja`, wstaw numer przez `-ldflags`

## Pułapki
- **Ścieżki względne w gotowym programie** — działa w projekcie, nie działa nigdzie indziej. Najczęstszy problem przy pierwszym "wydaniu".
- **README pisane dla siebie** — "uruchom i działa" nie jest instrukcją.
- **Binarki w repozytorium** — powinny być w `.gitignore`.
- **Testy pisane po fakcie, dopasowane do kodu** — sprawdzają, że kod robi to, co robi, a nie to, co powinien. Lepiej: test na przypadek, który kiedyś nie działał.
- **`go install` bez `PATH`** — program się instaluje, ale komenda "nie istnieje".
- **Brak obsługi `-h`** — `flag` daje ją za darmo (9.3), byle wywołać `flag.Parse()`.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **Kompilacja skrośna** działa bez dodatkowych narzędzi (`GOOS`/`GOARCH`) — o ile program nie używa cgo.
- **`go version -m -json zadania`** (1.25) — pokazuje, z jakich zależności i wersji Go zbudowano binarkę.
- **`go doc -http :8080`** (1.25) — do przeglądania dokumentacji własnego projektu.
- **`tool` w `go.mod`** (1.24) — jeśli projekt korzysta z narzędzi pomocniczych.
- **`go test` uruchamia `go vet`** domyślnie — część kontroli dostajesz za darmo.

## Notatki tutora
- **Kompilacja skrośna robi wrażenie.** Jedna komenda i uczeń ma program na Windows. Warto to pokazać nawet, jeśli nie ma gdzie tego uruchomić.
- **README jest ważniejsze, niż uczniowi się wydaje.** Dobre pytanie: "przeczytaj to jutro rano i sprawdź, czy sam byś zrozumiał".
- **Testy pisz razem z uczniem, ale nie za niego.** Pomóż wybrać, co testować — to trudniejsza decyzja niż samo pisanie.
- Jeśli uczeń nie zna gita — poświęć 15 minut na pięć komend. Bez tego straci pracę przy pierwszym nieudanym eksperymencie.
- **To moment na docenienie.** Uczeń przeszedł od `fmt.Println("Cześć")` do gotowego, przetestowanego narzędzia. Powiedz to wprost i konkretnie: wymień, co potrafi.
