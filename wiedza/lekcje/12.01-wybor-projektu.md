# Lekcja 12.1 — Wybór projektu

## Cel
Po lekcji uczeń:
- Wybiera projekt, który go interesuje i jest wykonalny w jego obecnym zakresie
- Rozpisuje go na etapy, z których **pierwszy** da się skończyć w jedną sesję
- Definiuje minimalną działającą wersję i odkłada resztę na później
- Ma założony moduł i szkielet projektu

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Wracamy do lekcji 1.1. Powiedziałeś wtedy, że chciałbyś kiedyś napisać [tu przypomnij, co zapisałeś w `notatki_tutora`]. Nadal chcesz?"

Jeśli notatki nie ma albo uczeń zmienił zdanie:
> "Co cię irytuje w codziennym używaniu komputera na tyle, że chciałbyś to zautomatyzować?"

**Drugie pytanie:**
> "Budujesz dom. Zaczynasz od dachu czy od fundamentów? A od czego zacząć program?"

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Umiesz już wszystko, czego potrzeba do prawdziwego narzędzia: pliki, JSON, argumenty, testy, błędy. Teraz najtrudniejsza rzecz w programowaniu: wybrać **odpowiednio mały** zakres."

**Kryteria dobrego projektu na tym etapie:**
| Kryterium | Dlaczego |
| --- | --- |
| Narzędzie wiersza poleceń | umiesz wszystkie klocki |
| Rozwiązuje **twój** prawdziwy problem | motywacja przetrwa trudny moment |
| Da się opisać jednym zdaniem | jeśli nie da się — jest za duże |
| Pierwsza działająca wersja w 2-3 sesje | za długo bez efektu = porzucone |
| Bez sieci, bazy danych i interfejsu graficznego | to poza kursem |

**Propozycje, jeśli uczeń nie ma pomysłu:**
| Projekt | Co ćwiczy |
| --- | --- |
| Lista zadań (dodaj / lista / zrobione / usuń) | JSON, argumenty, struktury |
| Notatnik z tagami i wyszukiwaniem | mapy, pliki, filtrowanie |
| Statystyki plików w katalogu (ile, jakie typy, rozmiar) | `os.ReadDir`, mapy, sortowanie |
| Generator haseł z opcjami | `math/rand/v2`, `flag`, walidacja |
| Licznik czasu pracy (start / stop / raport) | czas, JSON, formatowanie |
| Konwerter CSV → JSON | pliki, struktury, obsługa błędów |
| Zgadywanka liczbowa z tabelą wyników | pętle, losowanie, plik wyników |

## Krok 3 — Eksperyment (15-20 min)

**A. Jedno zdanie.** Uczeń zapisuje w `kurs/projekt/README.md`:
> "Program, który ____________ , żeby ____________ ."

Przykład: "Program, który przechowuje moje zadania w pliku JSON i pozwala je dodawać, oznaczać jako zrobione i wypisywać, żebym nie trzymał ich na karteczkach."

**Pytania kontrolne:**
- "Da się to powiedzieć bez słowa 'i' użytego trzy razy?"
- "Kto tego użyje?"
- "Skąd program weźmie dane, a gdzie je zapisze?"

**B. Lista funkcji — wszystkie, jakie przychodzą do głowy.** Bez oceniania. Uczeń pisze 8-12 pozycji.

**C. Podział na trzy etapy.** Uczeń przydziela każdą funkcję do jednego z etapów:
| Etap | Zawartość |
| --- | --- |
| **Etap 1 — najmniejsza działająca wersja** | absolutne minimum, które już jest do czegoś użyteczne |
| **Etap 2 — użyteczność** | to, bez czego byłoby to niewygodne |
| **Etap 3 — kiedyś** | pomysły, do których wrócisz (albo nie) |

Prowadź pytaniami:
- "Czy bez tej funkcji program jest **całkiem** bezużyteczny, czy tylko mniej wygodny?"
- "Gdyby zostały ci dwie godziny — co byś zrobił najpierw?"
- **Zasada:** etap 1 ma mieć maksymalnie **trzy** pozycje.

Przykład dla listy zadań:
- Etap 1: dodaj zadanie, wypisz listę, zapis do pliku
- Etap 2: oznacz jako zrobione, usuń, priorytety
- Etap 3: terminy, kategorie, kolorowanie, przypomnienia

**D. Szkielet projektu.** Uczeń zakłada strukturę (z 10.2):
```sh
mkdir -p kurs/projekt && cd kurs/projekt
go mod init zadania
```
```
kurs/projekt/
├── go.mod
├── README.md        ← jedno zdanie + etapy
└── main.go          ← na razie: wypisuje "start"
```
Uczeń uruchamia `go run .` i widzi, że szkielet żyje.

**E. Pierwsze zadanie na następną sesję.** Uczeń zapisuje w README konkret:
> "Następna sesja: struktura `Zadanie` i funkcja zapisująca slice zadań do `zadania.json`."

## Krok 4 — Pogłębienie (10 min)

**Projektowanie danych przed kodem** — najważniejsza decyzja projektu:
> "Zanim napiszesz jedną funkcję: jak wygląda **jedna sztuka** twoich danych?"

```go
type Zadanie struct {
	ID       int       `json:"id"`
	Tresc    string    `json:"tresc"`
	Zrobione bool      `json:"zrobione"`
	Dodano   time.Time `json:"dodano"`
}
```
**Pytania:**
- "Czy potrzebujesz identyfikatora? Po czym rozpoznasz konkretne zadanie w komendzie 'usuń'?"
- "Data — potrzebna w etapie 1 czy dopiero w 3?"
- "Co jest wartością zerową każdego pola i czy ma to sens?" (z 7.3)

**Szkic interfejsu użytkownika** — jak wygląda użycie:
```sh
zadania dodaj "kupić mleko"
zadania lista
zadania zrobione 3
```
> "Napisz te trzy linie **zanim** napiszesz kod. To twoja specyfikacja."

**Kolejność pracy w każdej sesji:**
1. najmniejszy działający kawałek
2. sprawdzenie, że działa (uruchomienie)
3. test do tego kawałka (10.1)
4. dopiero potem następny kawałek

**Czego nie robić na starcie:**
- nie projektuj pakietów z góry — podzielisz, gdy urośnie (10.2)
- nie dodawaj bibliotek zewnętrznych, dopóki nie wiesz, że są potrzebne
- nie zaczynaj od współbieżności (11.3)
- nie optymalizuj czegoś, co jeszcze nie działa

## Krok 5 — Ćwiczenie
Ćwiczeniem jest sam projekt. Uczeń kończy sesję mając:
- [ ] `kurs/projekt/README.md` z jednym zdaniem i trzema etapami
- [ ] `go.mod` (`go mod init`)
- [ ] `main.go` wypisujący cokolwiek i uruchamiający się
- [ ] szkic struktury danych
- [ ] trzy przykładowe wywołania z wiersza poleceń
- [ ] zapisane pierwsze zadanie na następną sesję

## Pułapki
- **Za duży projekt** — najczęstsza przyczyna porzucenia. Jeśli uczeń mówi "klon Trello" — pomóż zawęzić do jednej funkcji.
- **Projekt bez osobistego zainteresowania** — zabraknie paliwa przy pierwszym trudnym błędzie.
- **Projektowanie wszystkiego z góry** — dwie godziny diagramów, zero kodu.
- **Zaczynanie od najtrudniejszej części** — zacznij od czegoś, co da widoczny efekt w 20 minut.
- **"Najpierw nauczę się jeszcze X"** — nie. Uczeń umie wystarczająco. Brakującą wiedzę dobierze w trakcie.
- **Etap 1 z ośmioma pozycjami** — to nie jest etap 1.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
Jeśli projekt potrzebuje unikalnych identyfikatorów — **pakiet `uuid` jest w bibliotece standardowej od Go 1.27**. Wcześniej wymagało to `github.com/google/uuid`. Dla listy zadań zwykły licznik `int` wystarczy i jest czytelniejszy.

## Notatki tutora
- **To lekcja rozmowy, nie kodu.** Twoja rola: zawężać zakres pytaniami, nie proponować rozwiązań.
- **Sprawdź `notatki_tutora`** — jeśli w 1.1 zapisałeś pomysł ucznia, wróć do niego. Domknięcie łuku po całym kursie robi duże wrażenie.
- **Trzy pozycje w etapie 1 to twarda granica.** Uczeń będzie chciał więcej. Powiedz: "wszystko z listy zrobisz — tylko nie naraz".
- **Nie pisz kodu za ucznia** — zasada obowiązuje w projekcie tym bardziej. Możesz pomóc rozpisać kroki, przejrzeć kod, zadać pytanie naprowadzające.
- Jeśli uczeń chce projektu webowego mimo ostrzeżeń — nie zabraniaj, ale zaproponuj etap 1 jako narzędzie wiersza poleceń z tą samą logiką. Warstwę HTTP dołoży później, gdy pozna `net/http` (12.4).
- Zapisz wybrany projekt do `postep`: `add-notatka` — będziesz do niego wracał w 12.2 i 12.3.
