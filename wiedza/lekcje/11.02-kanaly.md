# Lekcja 11.2 — Kanały

## Cel
Po lekcji uczeń:
- Tworzy kanał, wysyła i odbiera przez niego wartości
- Rozumie, że kanał **synchronizuje**: odbiór czeka na wysyłkę
- Zamyka kanał i iteruje po nim przez `range`
- Rozpoznaje zakleszczenie i wie, skąd się bierze

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Kuchnia i sala w restauracji. Kucharz stawia gotowe danie w okienku podawczym, kelner je zabiera. Co się dzieje, gdy kelner przyjdzie, a okienko jest puste?"

→ czeka.

**Drugie pytanie:**
> "A gdy kucharz ma danie, ale w okienku nie ma miejsca?"

→ czeka.

**Trzecie:**
> "Czy kucharz i kelner muszą się umawiać na godzinę? Skąd wiedzą, kiedy działać?"

→ okienko samo ich synchronizuje.

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Kanał to dokładnie takie okienko. Jedna goroutine wkłada, druga wyjmuje, a czekanie dzieje się samo."

Uczeń tworzy `kurs/zadania/31-kanaly/main.go`:

```go
package main

import "fmt"

func main() {
	okienko := make(chan string)

	go func() {
		okienko <- "makaron gotowy"
	}()

	danie := <-okienko
	fmt.Println("kelner odebrał:", danie)
}
```

**Pytania:**
- "`chan string` — co to znaczy?" → kanał przenoszący teksty
- "`okienko <- \"...\"` a `<-okienko` — jak zapamiętać, co jest czym?" → strzałka pokazuje kierunek przepływu danych
- "Usuń `go` przed funkcją i uruchom." → `fatal error: all goroutines are asleep - deadlock!`
  > "Czemu? Kto miałby odebrać, skoro `main` stoi zablokowany na wysyłce?"

Nazwij: **kanał**, **wysłanie**, **odbiór**, **zakleszczenie (deadlock)**.

## Krok 3 — Eksperyment (15-20 min)

1. **Kanał czeka** — uczeń dodaje wypisywanie, żeby zobaczyć kolejność:
   ```go
   okienko := make(chan string)

   go func() {
       fmt.Println("kucharz: zaczynam")
       time.Sleep(500 * time.Millisecond)
       fmt.Println("kucharz: wkładam do okienka")
       okienko <- "makaron"
       fmt.Println("kucharz: oddane")
   }()

   fmt.Println("kelner: czekam")
   danie := <-okienko
   fmt.Println("kelner: mam", danie)
   ```
   > "Prześledź kolejność wypisów. Kto na kogo czekał?"
2. **Kilka wyników z kilku goroutine:**
   ```go
   wyniki := make(chan int)

   for i := 1; i <= 3; i++ {
       go func() {
           wyniki <- i * i
       }()
   }

   for range 3 {
       fmt.Println(<-wyniki)
   }
   ```
   > "Uruchom kilka razy. Ta sama kolejność?" → nie, zależy od tego, która goroutine zdąży pierwsza
   > "To rozwiązuje problem z 11.1: jak przekazać wynik z goroutine **bez** wyścigu."
3. **Kanał z buforem:**
   ```go
   z := make(chan int, 3)     // okienko na 3 dania

   z <- 1
   z <- 2
   z <- 3
   fmt.Println("trzy wysłane, nikt nie odbierał")
   // z <- 4                  // to by już zablokowało

   fmt.Println(<-z, <-z, <-z)
   ```
   > "Czym się różni od kanału bez bufora?" → wysyłający nie czeka, dopóki jest miejsce
   > "Ile miejsca zajętego?" → `len(z)`, pojemność: `cap(z)` — jak w slice (4.2)
4. **Zamykanie i `range`:**
   ```go
   linia := make(chan string)

   go func() {
       defer close(linia)
       for _, d := range []string{"zupa", "drugie", "deser"} {
           linia <- d
       }
   }()

   for danie := range linia {
       fmt.Println("podano:", danie)
   }
   fmt.Println("koniec obiadu")
   ```
   > "Skąd pętla `range` wie, że ma się skończyć?" → z `close`
   > "Usuń `close` i uruchom." → zakleszczenie: pętla czeka na kolejną wartość, która nigdy nie przyjdzie
   > "Kto powinien zamykać kanał — wysyłający czy odbierający?" → **zawsze wysyłający**. Odbierający nie wie, czy będzie więcej.
5. **Odbiór z zamkniętego kanału:**
   ```go
   c := make(chan int, 1)
   c <- 5
   close(c)

   v, ok := <-c
   fmt.Println(v, ok)      // 5 true
   v, ok = <-c
   fmt.Println(v, ok)      // 0 false — kanał zamknięty i pusty
   ```
   > "Znowu `wartość, ok`. Czwarty raz w kursie — gdzie były poprzednie?" → mapa (4.3), asercja typu (8.2), `strconv` (2.4)
6. **Kanały jednokierunkowe** — dokumentacja intencji:
   ```go
   func producent(wyj chan<- int) { wyj <- 1; close(wyj) }
   func konsument(wej <-chan int) { fmt.Println(<-wej) }
   ```
   > "`chan<-` tylko do wysyłania, `<-chan` tylko do odbioru. Kompilator pilnuje. Po co to?" → żeby funkcja nie mogła zrobić czegoś, czego nie powinna

## Krok 4 — Pogłębienie (10 min)

**Kanał czy `WaitGroup`?**
| Potrzebujesz | Użyj |
| --- | --- |
| Poczekać, aż wszystko się skończy | `WaitGroup` |
| Odebrać **wyniki** z goroutine | kanał |
| Przekazywać strumień danych | kanał |
| Jedna goroutine ma sygnalizować drugiej | kanał |

**Motto Go:**
> "Nie komunikuj się przez współdzielenie pamięci — współdziel pamięć przez komunikację."

Znaczy: zamiast dawać dwóm goroutine dostęp do jednej zmiennej i pilnować zamków, **przekaż wartość kanałem**. Wtedy w danym momencie tylko jedna strona ją ma.

**Wzorzec: zbieranie wyników z zachowaniem kolejności:**
```go
type Wynik struct {
	Nr     int
	Wartosc int
}

wyniki := make(chan Wynik, 3)
for i := range 3 {
	go func() { wyniki <- Wynik{Nr: i, Wartosc: i * i} }()
}

posortowane := make([]int, 3)
for range 3 {
	w := <-wyniki
	posortowane[w.Nr] = w.Wartosc     // indeks przywraca kolejność
}
```
> "Kanał nie gwarantuje kolejności. Jeśli jej potrzebujesz — dołóż numer."

**Kanał `nil`** — wysyłka i odbiór blokują na zawsze. Rzadkie, ale przy zakleszczeniu warto sprawdzić, czy kanał został utworzony przez `make`.

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "kanały". Sugerowane:
- 🔥 Goroutine wysyła pięć liczb kanałem, `main` je odbiera i sumuje
- ⭐ Trzy goroutine liczą sumy trzech slice'ów i odsyłają wyniki kanałem; `main` sumuje wszystkie trzy
- ⚡ Producent-konsument: jedna goroutine generuje liczby 1-20 do kanału i zamyka go, druga odbiera i wypisuje tylko parzyste; `main` czeka na zakończenie obu

Kod ucznia: `kurs/zadania/31-kanaly/`.

## Pułapki
- **Wysyłka bez odbiorcy** → zakleszczenie. Najczęstszy błąd: wysyłka w `main` bez goroutine po drugiej stronie.
- **Odbiór bez wysyłającego** → to samo.
- **Brak `close` przy pętli `range`** → pętla czeka wiecznie.
- **Zamykanie przez odbierającego** → wysyłający dostanie panikę `send on closed channel`.
- **Podwójne `close`** → panika.
- **Wysyłka do zamkniętego kanału** → panika (odbiór z zamkniętego jest bezpieczny).
- **Kanał bez `make`** (`var c chan int`) → `nil`, blokuje na zawsze.
- **Bufor jako "naprawa" zakleszczenia** — jeśli program działa dopiero po dodaniu bufora, prawdopodobnie ukryłeś prawdziwy problem, a nie go rozwiązałeś.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **Kanały zegara** (`time.After`, `Ticker`) od 1.23 są **niebuforowane** i nie zostawiają nieświeżych wartości po `Reset`/`Stop`; nieużywane zegary są sprzątane od razu. Praktycznie: mniej wycieków, mniej niespodzianek.
- Iteratory (`range` po funkcji, 1.23) bywają dziś używane tam, gdzie kiedyś dawano kanał do przekazywania strumienia danych — i są tańsze. Wzmianka; kanały nadal są właściwym narzędziem do komunikacji **między goroutine**.

## Notatki tutora
- **Analogia z okienkiem podawczym niesie całą lekcję.** Trzymaj się jej: kanał bez bufora = okienko na jedno danie, z buforem = półka na kilka.
- **Zakleszczenie warto wywołać celowo** (eksperyment 1 i 4). Uczeń musi zobaczyć komunikat `all goroutines are asleep - deadlock!` w bezpiecznych warunkach i wiedzieć, że to nie katastrofa, tylko informacja.
- **Nie wprowadzaj `select`** — to 11.3. Jeśli uczeń pyta "a jak czekać na dwa kanały naraz" → "brawo, następna lekcja".
- Nie wprowadzaj `context`, pul roboczych ani wzorców rozgałęziania. Poza kursem.
- Jeśli uczeń gubi się w strzałkach — poradź prostą sztuczkę: **strzałka zawsze pokazuje, dokąd płyną dane**. `c <- x` do kanału, `<-c` z kanału.
