# Lekcja 1.3 — Edytor, terminal i `gofmt`

## Cel
Po lekcji uczeń:
- Ma skonfigurowany edytor z rozszerzeniem Go (formatowanie przy zapisie)
- Zna pętlę pracy: pisz → zapisz → `go run` → przeczytaj wynik → popraw
- Rozumie, dlaczego cały kod w Go wygląda tak samo i dlaczego to jego zysk
- Umie sprawdzić kod trzema narzędziami: `gofmt`, `go vet`, `go build`

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Czytałeś kiedyś czyjeś odręczne notatki — cudzy charakter pisma, własne skróty, strzałki na marginesie? Ile czasu zajmuje przyzwyczajenie się do cudzego sposobu zapisu, zanim w ogóle dotrzesz do treści?"

**Drugie pytanie:**
> "A gdyby wszyscy na świecie pisali notatki dokładnie tym samym krojem, z tymi samymi odstępami — co byś zyskał, a co stracił?"

**Co chcesz usłyszeć:** zysk = czytasz od razu treść, bez rozszyfrowywania formy. Strata = brak własnego stylu (i tu warto zapytać: a czy styl zapisu w ogóle jest wart tej straty?).

## Krok 2 — Mostek (5 min)
**Mostek:**
> "Go podjęło tę decyzję za wszystkich. Jest jedno narzędzie, `gofmt`, i ono ustala jak kod wygląda: wcięcia, odstępy, wyrównanie. Nie ma dyskusji o stylu, bo nie ma opcji do wyboru."

**Uczeń psuje formatowanie własnego pliku** — celowo, w edytorze. `kurs/zadania/01-hello/main.go`:

```go
package main
import "fmt"
func main(){
fmt.Println("Cześć, tu Go!")
      fmt.Println("druga linia")
}
```

Uruchomienie: `go run ./01-hello` → **program działa**. Kompilator nie ma nic przeciwko.

**Pytanie:** "Program działa. To po co się przejmować wyglądem?"

Teraz uczeń wykonuje:
```sh
gofmt -d 01-hello/main.go     # pokaż różnicę (nic nie zmienia)
gofmt -w 01-hello/main.go     # zapisz poprawioną wersję
```
i patrzy w edytor.

**Pytanie:** "Co się zmieniło? Czego byś sam nie poprawił?"

## Krok 3 — Eksperyment (10-15 min)

1. **Konfiguracja edytora.** VS Code + oficjalne rozszerzenie **Go** (wydawca: Go Team at Google).
   Po instalacji rozszerzenie samo zaproponuje doinstalowanie narzędzi (`gopls`) — uczeń się zgadza.
   Sprawdzenie: uczeń psuje wcięcia, zapisuje plik (Ctrl+S / Cmd+S), wcięcia same wracają na miejsce.
   **Zapytaj:** "Zadziałało? Jeśli tak — od teraz nie myślisz już o formatowaniu."

2. **Pętla pracy.** Uczeń ustawia okna: edytor po lewej, terminal po prawej (albo terminal wbudowany w VS Code: Ctrl+`).
   Cykl, który powtórzy setki razy:
   ```
   pisz w edytorze  →  Ctrl+S  →  go run ./katalog  →  czytaj wynik  →  popraw
   ```
   Uczeń przechodzi ten cykl 3 razy, zmieniając cokolwiek w tekście.

3. **Trzy narzędzia sprawdzające** — uczeń uruchamia każde na swoim pliku:
   ```sh
   gofmt -l .              # które pliki są źle sformatowane (lista nazw; pusto = OK)
   go vet ./01-hello       # podejrzane konstrukcje, które się kompilują, ale pachną błędem
   go build ./01-hello     # czy w ogóle się kompiluje
   ```
   **Zapytaj po każdym:** "Co ci powiedziało? Cisza to dobra wiadomość czy zła?"
   → W narzędziach Go **cisza znaczy: wszystko w porządku**. To konwencja, którą uczeń spotka wszędzie.

4. Uczeń sprawdza `go vet` na czymś podejrzanym — wstaw do `main`:
   ```go
   fmt.Printf("%d\n", "tekst")
   ```
   `go build` przejdzie (albo nie, zależnie od wersji), `go vet` powie wprost:
   `Printf format %d has arg "tekst" of wrong type string`
   **Zapytaj:** "Kompilator to przepuścił, `go vet` nie. Do czego więc służy `vet`?"

## Krok 4 — Pogłębienie (10 min)

**Porządek w katalogu zadań.** Uczeń ogląda strukturę:
```
kurs/zadania/
├── go.mod            ← "tu zaczyna się projekt" (szczegóły w 10.2)
├── 01-hello/
│   └── main.go
└── 02-zmienne/       ← powstanie w następnej lekcji
    └── main.go
```
**Zasada na cały kurs:** jedno zadanie = jeden podkatalog = jeden plik `main.go` z `package main`.
Uruchomienie zawsze z katalogu `kurs/zadania`: `go run ./01-hello`.

**Pytania:**
- "Czemu każde zadanie ma osobny katalog, a nie wszystkie pliki w jednym?"
  → bo w jednym katalogu może być tylko jedna funkcja `main` (uczeń widział ten błąd w 1.2)

**Tabulator czy spacje?** Go używa **tabulatorów**. Nie musisz o tym pamiętać — `gofmt` wstawia je sam. Jeśli uczeń zobaczy w internecie dyskusję "tabs vs spaces", w Go ta dyskusja nie istnieje.

**Komentarze** — wprowadź teraz, przydadzą się od następnej lekcji:
```go
// komentarz do końca linii

/* komentarz
   przez wiele linii */
```
**Zapytaj:** "Komputer je ignoruje. Więc dla kogo one są?"

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "workflow i formatowanie". Sugerowane:
- 🔥 Rozwal formatowanie własnego programu tak brzydko, jak potrafisz (bez psucia działania), potem `gofmt -w`
- ⭐ Zrób katalog `02-proba`, napisz w nim program wypisujący 3 linie, dodaj do każdej komentarz wyjaśniający
- ⚡ Znajdź błąd, który przepuszcza `go build`, a łapie `go vet` (podpowiedź: `Printf` i niepasujący typ)

## Pułapki
- **Edytor bez rozszerzenia Go** — uczeń traci autouzupełnianie, podpowiedzi i automatyczne formatowanie. To najgorszy możliwy start. Warto poświęcić te 10 minut na konfigurację.
- **Notatnik / TextEdit / Word** — Word wstawia "inteligentne" cudzysłowy (`"` zamiast `"`), których Go nie rozumie. **Nigdy** nie pisz kodu w edytorze tekstu sformatowanego.
- **`gofmt -w` na pliku, który się nie parsuje** — nie zadziała. `gofmt` musi zrozumieć kod, żeby go sformatować. Jeśli nic się nie dzieje po zapisie — najpierw popraw składnię.
- **Uczeń zgubiony w terminalu** — jeśli `go run ./01-hello` mówi `directory not found`, uczeń jest w złym katalogu. `pwd` pokazuje gdzie jesteś, `cd` przenosi, `ls` pokazuje zawartość.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`go doc -http :8080`** (1.25) — cała dokumentacja Go lokalnie w przeglądarce, działa bez internetu. Pokaż uczniowi, będzie wracał.
- **`go fix ./...`** (przebudowane w 1.26) — automatycznie modernizuje kod do nowszych idiomów. **Nie pokazuj tego jeszcze** — uczeń nie ma czego modernizować. Wraca w 10.3.
- Źródło (`71-skladnia.md`) porównuje formatowanie Go do innych języków. Pomiń — uczeń nie zna innych języków.

## Notatki tutora
- To lekcja **narzędziowa**, nie konceptualna. Jeśli uczeń jest zniecierpliwiony ("kiedy w końcu kod?") — powiedz, że to ostatnia lekcja przygotowawcza, i skróć do konfiguracji edytora + pętli pracy.
- **Zapisz w `student.json` (`srodowisko.edytor`)**, czego uczeń używa — będziesz do tego wracał przy instrukcjach.
- Jeśli uczeń nie umie obsługiwać terminala (`cd`, `ls`, `pwd`) — **zatrzymaj się tutaj**. Dziesięć minut na te trzy komendy oszczędzi godziny frustracji w całym kursie. Dopisz do `do_powtorki`.
- Nie tłumacz, jak `gofmt` działa w środku (parser, AST). Uczeń ma go używać, nie rozumieć.
