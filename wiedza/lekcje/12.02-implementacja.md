# Lekcja 12.2 — Implementacja

## Cel
Po lekcji (a właściwie po serii sesji) uczeń:
- Ma działający etap 1 swojego projektu
- Pracuje małymi krokami: kawałek → uruchomienie → sprawdzenie
- Sam rozpoznaje, kiedy funkcja jest za długa i trzeba ją podzielić
- Wie, gdzie szukać, gdy czegoś nie umie

## Krok 1 — Zakotwiczenie (5 min, na pierwszej sesji)
**Pytanie wejściowe:**
> "Masz przed sobą pusty plik i listę trzech funkcji z etapu 1. Od czego zaczynasz?"

**Naprowadź:**
> "Która z tych trzech rzeczy da się sprawdzić **najszybciej**? Nie która jest najważniejsza — która najszybciej pokaże, że coś działa."

## Krok 2 — Mostek (10 min, na pierwszej sesji)
**Mostek:**
> "Zasada na cały projekt: **zawsze miej działający program.** Nie pisz stu linii, żeby dopiero potem uruchomić. Pisz dziesięć, uruchom, sprawdź, pisz kolejne dziesięć."

**Cykl pracy — wypisz uczniowi i wracaj do niego:**
```
1. Wybierz NAJMNIEJSZY kawałek, który da się sprawdzić
2. Napisz go
3. Uruchom (go run .)
4. Sprawdź, czy robi to, czego oczekiwałeś
5. Działa? → test (go test) → następny kawałek
   Nie działa? → metoda debugowania z 10.3
```

**Przykładowa rozpiska pierwszej sesji (lista zadań):**
| Krok | Kawałek | Sprawdzenie |
| --- | --- | --- |
| 1 | struktura `Zadanie` + slice na sztywno w kodzie | wypisuje się |
| 2 | funkcja `wypisz(zadania []Zadanie)` | ładna lista |
| 3 | zapis do JSON (9.2) | plik istnieje, `cat` pokazuje treść |
| 4 | odczyt z JSON | wczytane = zapisane |
| 5 | brak pliku → pusta lista, nie błąd | pierwsze uruchomienie działa |
| 6 | argument `dodaj` (9.3) | `go run . dodaj "test"` dodaje |

> "Sześć kroków, każdy sprawdzalny w minutę. Po każdym program **działa** — tylko robi mniej."

## Krok 3 — Eksperyment (każda kolejna sesja)

**Prowadzenie sesji projektowej — schemat dla agenta:**

1. **Start (5 min):** "Co zrobiłeś od ostatniego razu? Co działa, co nie?"
   Uczeń uruchamia program i pokazuje stan.
2. **Cel sesji (5 min):** "Co chcesz mieć na końcu dzisiejszej sesji?"
   Jeśli cel jest za duży — zawężaj pytaniami: "a da się to podzielić na dwie części, z których pierwsza już coś daje?"
3. **Praca (40 min):** uczeń pisze, agent pyta.
   - gdy uczeń utyka: "co dokładnie ma się stać w tym miejscu? powiedz słowami"
   - gdy błąd: "co powiedział kompilator? którą linię wskazał?"
   - gdy działa: "sprawdź przypadek brzegowy — co przy pustej liście?"
4. **Zamknięcie (10 min):** uruchomienie całości, `gofmt`, `go vet`, `go test`. Zapis następnego kroku w README.

**Pytania, które warto zadawać w trakcie:**
| Sytuacja | Pytanie |
| --- | --- |
| Funkcja rośnie ponad ekran | "da się z tego wyjąć kawałek z własną nazwą?" |
| Powtórzony fragment | "widzisz to samo w dwóch miejscach — co z tym zrobisz?" |
| Zignorowany `err` | "co się stanie, gdy ta operacja się nie uda?" |
| Zagnieżdżone `if` | "pamiętasz wczesne wyjście z 3.1?" |
| Kod, który działa "cudem" | "wytłumacz mi linia po linii, co się tu dzieje" |
| Uczeń chce dodać funkcję z etapu 3 | "czy etap 1 jest skończony?" |

**Gdy uczeń nie umie czegoś, czego nie było w kursie** (np. czas, losowanie, sortowanie po polu):
> "Nie znasz tego — i tak właśnie wygląda codzienna praca. Sprawdź: `go doc time`. Albo `pkg.go.dev/time`. Znajdź funkcję i przeczytaj, co zwraca."
**To ważna umiejętność sama w sobie.** Nie podawaj gotowca — pokaż, gdzie szukać.

## Krok 4 — Pogłębienie (rozłożone na sesje)

**Kiedy dzielić na pliki i pakiety** (5.3, 10.2):
- `main.go` powyżej ~200 linii → wydziel `zadania.go`, `plik.go`
- osobna odpowiedzialność, którą da się nazwać → osobny plik
- pakiet w podkatalogu dopiero, gdy plików jest kilka i mają wspólny temat

**Typowa struktura dojrzalszego projektu:**
```
projekt/
├── go.mod
├── README.md
├── main.go            ← argumenty, wywołanie logiki, kody wyjścia
├── zadanie.go         ← struktura i operacje na niej
├── zadanie_test.go
├── magazyn.go         ← zapis/odczyt JSON
└── magazyn_test.go
```

**Rozdzielenie warstw** — zasada, która się opłaca:
```go
// ŹLE — funkcja liczy i wypisuje
func policzIWypisz(z []Zadanie) { fmt.Println(len(z)) }

// LEPIEJ — funkcja liczy, main wypisuje
func policzNiezrobione(z []Zadanie) int { ... }
```
> "Czemu to lepsze?" → da się przetestować (10.1) bez czytania ekranu; da się użyć w innym miejscu

**Gdy projekt utyka** — pytania ratunkowe:
- "co dokładnie nie działa? pokaż najmniejszy przypadek"
- "kiedy ostatnio działało? co się zmieniło od tamtej pory?"
- "czy to musi być w etapie 1?"

## Krok 5 — Ćwiczenie
Ćwiczeniem jest projekt. Kryteria zakończenia etapu 1:
- [ ] program robi to, co obiecuje jedno zdanie z README
- [ ] uruchamia się bez paniki na typowych danych
- [ ] obsługuje przynajmniej trzy błędne sytuacje (brak pliku, złe argumenty, uszkodzone dane)
- [ ] `gofmt -l .` milczy
- [ ] `go vet ./...` milczy
- [ ] ma co najmniej dwa testy

## Pułapki
- **Pisanie 200 linii przed pierwszym uruchomieniem** — potem trzy błędy naraz i nie wiadomo, który jest który.
- **Dodawanie funkcji z etapu 2 przed skończeniem etapu 1** — projekt nigdy nie osiąga stanu "działa".
- **Przepisywanie od zera przy pierwszym problemie** — prawie zawsze lepiej naprawić.
- **Kopiowanie kodu z internetu bez zrozumienia** — działa do pierwszej zmiany. Zasada: jeśli nie umiesz wytłumaczyć linii, nie wklejaj jej.
- **Odkładanie obsługi błędów "na potem"** — potem znaczy nigdy, a dopisanie jej później oznacza przepisanie logiki.
- **Perfekcjonizm w nazwach i strukturze** — działający kod z niedoskonałą nazwą bije doskonały projekt bez kodu.

## Notatki tutora
- **Ta lekcja trwa kilka sesji.** Prowadź ją wielokrotnie, za każdym razem od kroku 3 (schemat sesji projektowej).
- **Nie pisz kodu za ucznia — nigdy, a w projekcie szczególnie.** Wolno: zadać pytanie, wskazać lekcję do przypomnienia, pokazać w dokumentacji, przejrzeć gotowy kod.
- **Chwal konkretnie i często.** Projekt to najdłuższy odcinek kursu bez wyraźnych "poziomów"; uczeń łatwo traci poczucie postępu. Pokazuj, ile już działa.
- **Pilnuj zakresu.** Uczeń będzie chciał dokładać. Odpowiedź: "zapisz do etapu 3, wrócimy".
- **Jeśli uczeń utknął na dwie sesje** w tym samym miejscu — coś jest za trudne. Zaproponuj uproszczenie: mniej pól, prostszy format, mniej przypadków.
- Aktualizuj `postep` po każdej sesji projektowej, nawet jeśli lekcja `12.2` nie jest jeszcze "skończona" — użyj `add-notatka` z opisem, co powstało.
