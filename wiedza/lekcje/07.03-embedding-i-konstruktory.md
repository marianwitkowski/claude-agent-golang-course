# Lekcja 7.3 — Osadzanie, wartości zerowe, konstruktory

## Cel
Po lekcji uczeń:
- Osadza jedną strukturę w drugiej i korzysta z pól oraz metod bez podawania ścieżki
- Rozumie, dlaczego Go ma osadzanie zamiast dziedziczenia
- Projektuje strukturę tak, by jej wartość zerowa była użyteczna
- Pisze konstruktor tam, gdzie tworzenie wymaga sprawdzenia poprawności

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Opisujesz pracownika firmy. Ma imię, wiek i miasto — jak każda osoba. Ale ma też stanowisko i pensję. Napisałbyś wszystkie pola od nowa, czy powiedziałbyś: 'to osoba, plus stanowisko i pensja'?"

**Drugie pytanie:**
> "'Pracownik **jest** osobą' czy 'pracownik **ma** dane osobowe'? Czy widzisz różnicę między tymi zdaniami?"

→ Go stawia na drugie sformułowanie. Zaraz zobaczy dlaczego.

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Możesz włożyć jedną strukturę w drugą. Jeśli zrobisz to **bez nazwy pola**, Go pozwoli sięgać po pola wewnętrznej struktury bezpośrednio. To się nazywa osadzanie (embedding)."

Uczeń tworzy `kurs/zadania/21-osadzanie/main.go`:

```go
package main

import "fmt"

type Osoba struct {
	Imie string
	Wiek int
}

func (o Osoba) Przedstaw() string {
	return fmt.Sprintf("%s, lat %d", o.Imie, o.Wiek)
}

type Pracownik struct {
	Osoba              // osadzenie — bez nazwy pola!
	Stanowisko string
	Pensja     float64
}

func main() {
	p := Pracownik{
		Osoba:      Osoba{Imie: "Anna", Wiek: 30},
		Stanowisko: "programistka",
		Pensja:     12000,
	}

	fmt.Println(p.Imie)          // bez p.Osoba.Imie!
	fmt.Println(p.Przedstaw())   // metoda też się "przeniosła"
	fmt.Println(p.Osoba.Imie)    // pełna ścieżka też działa
}
```

**Pytania:**
- "Czym różni się `Osoba` w tej strukturze od pola `Stanowisko string`?" → nie ma nazwy pola, jest sam typ
- "`p.Imie` działa, choć `Pracownik` nie ma pola `Imie`. Skąd Go je wziął?"
- "`p.Przedstaw()` też zadziałało. Co jeszcze się 'przeniosło'?" → metody osadzonego typu

## Krok 3 — Eksperyment (15 min)

1. **Osadzenie z nazwą — dla porównania:**
   ```go
   type Pracownik2 struct {
       Dane       Osoba        // zwykłe pole, z nazwą
       Stanowisko string
   }

   p2 := Pracownik2{Dane: Osoba{Imie: "Piotr"}, Stanowisko: "tester"}
   fmt.Println(p2.Dane.Imie)     // działa
   // fmt.Println(p2.Imie)       // BŁĄD: p2.Imie undefined
   ```
   > "Jedna różnica w deklaracji, duża w użyciu. Kiedy wolisz którą wersję?"
2. **Przesłanianie metody:**
   ```go
   func (p Pracownik) Przedstaw() string {
       return fmt.Sprintf("%s, %s", p.Imie, p.Stanowisko)
   }

   fmt.Println(p.Przedstaw())        // wersja Pracownika
   fmt.Println(p.Osoba.Przedstaw())  // wersja Osoby — nadal dostępna
   ```
   > "Która wersja zadziałała domyślnie? Czy stara zniknęła?"
   → wygrywa "zewnętrzna", ale wewnętrzna jest dostępna pełną ścieżką. Nic nie znika.
3. **To nie jest dziedziczenie** — kluczowy eksperyment:
   ```go
   func opiszOsobe(o Osoba) string { return o.Przedstaw() }

   // fmt.Println(opiszOsobe(p))       // BŁĄD: cannot use p (Pracownik) as Osoba
   fmt.Println(opiszOsobe(p.Osoba))    // OK — podajemy osadzoną część
   ```
   > "W językach z dziedziczeniem `Pracownik` **byłby** `Osobą` i przeszedłby bez zmian. W Go tak nie jest."
   > "Wróć do pytania z kroku 1: 'jest' czy 'ma'? Go mówi: **ma**."
   Sposobem na "przekazuj cokolwiek potrafi X" są interfejsy — następna lekcja.
4. **Wartość zerowa, która działa** — projektowanie struktur:
   ```go
   type Licznik struct {
       n int
   }

   func (l *Licznik) Zwieksz() { l.n++ }
   func (l Licznik) Wartosc() int { return l.n }

   func main() {
       var l Licznik      // bez konstruktora, sama wartość zerowa
       l.Zwieksz()
       l.Zwieksz()
       fmt.Println(l.Wartosc())   // 2
   }
   ```
   > "Nie było żadnej inicjalizacji, a działa. To celowa zasada projektowania w Go: **wartość zerowa powinna być użyteczna**."
   Kontrprzykład, który uczeń zna: mapa. `var m map[string]int` **nie** jest użyteczna do zapisu (4.3) — i to jest wyjątek, który wszystkich uwiera.
5. **Kiedy konstruktor jest potrzebny:**
   ```go
   type Kolejka struct {
       elementy []string
       maks     int
   }

   func NowaKolejka(maks int) (*Kolejka, error) {
       if maks <= 0 {
           return nil, errors.New("maks musi być dodatni")
       }
       return &Kolejka{elementy: []string{}, maks: maks}, nil
   }
   ```
   > "Czemu tu wartość zerowa nie wystarczy?" → bo `maks` równy 0 nie ma sensu, a poprawność trzeba sprawdzić

## Krok 4 — Pogłębienie (10 min)

**Osadzanie wskaźnika:**
```go
type Pracownik struct {
	*Osoba
	Stanowisko string
}
```
> "Działa tak samo, ale osadzona część może być `nil` — i wtedy `p.Imie` panikuje. Kiedy to ma sens?" → gdy część danych bywa nieobecna. Dla początkującego: **osadzaj wartość, nie wskaźnik.**

**Konflikt nazw:**
```go
type A struct{ X int }
type B struct{ X int }
type C struct {
	A
	B
}

c := C{}
// c.X = 1      // BŁĄD: ambiguous selector c.X
c.A.X = 1       // trzeba wprost
```
> "Go nie zgaduje. Gdy dwie osadzone struktury mają to samo pole, musisz powiedzieć, o którą chodzi."

**Konwencje nazewnicze konstruktorów:**
| Sytuacja | Nazwa |
| --- | --- |
| Pakiet ma jeden główny typ | `New()` — np. `bufio.NewScanner` |
| Pakiet ma kilka typów | `NowyKlient()`, `NowaKolejka()` |
| Tworzenie może się nie udać | zwraca `(*T, error)` |
| Tworzenie zawsze się udaje | zwraca `*T` albo `T` |

**Struktura z wieloma opcjami** — problem braku argumentów domyślnych w Go (z 5.1):
```go
type Opcje struct {
	Timeout  int
	Powtorki int
	Debug    bool
}

func Uruchom(o Opcje) { ... }

Uruchom(Opcje{Timeout: 30})   // reszta bierze wartości zerowe
```
> "To jest odpowiedź Go na argumenty nazwane i domyślne: struktura z opcjami. Wartości zerowe stają się wartościami domyślnymi — i tu widać, po co ta zasada projektowania."

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "osadzanie i konstruktory". Sugerowane:
- 🔥 `Zwierze` (imię, wiek) osadzone w `Pies` (rasa); wypisz imię psa bez pełnej ścieżki
- ⭐ `Pojazd` z metodą `Opis()` osadzony w `Samochod`; przesłoń `Opis()` i pokaż obie wersje
- ⚡ `Koszyk` z konstruktorem `NowyKoszyk(limit int) (*Koszyk, error)` i metodami `Dodaj(produkt) error` (błąd po przekroczeniu limitu) oraz `Suma() float64`

## Pułapki
- **Mylenie osadzania z dziedziczeniem** — `Pracownik` nie jest `Osobą` i nie przejdzie tam, gdzie oczekiwana jest `Osoba`. Eksperyment 3 to pokazuje.
- **Osadzony wskaźnik równy `nil`** → panika przy sięganiu po pole. Osadzaj wartości.
- **Konflikt nazw pól** — kompilator zgłasza `ambiguous selector` dopiero przy użyciu, nie przy deklaracji.
- **Zbyt głębokie osadzanie** — trzy poziomy i już nie wiadomo, skąd pochodzi pole. Płasko jest lepiej.
- **Konstruktor, który tylko ustawia pola** — zbędny. Jeśli `Struktura{A: 1, B: 2}` wystarcza, nie pisz funkcji.
- **Wartość zerowa bezużyteczna z powodu mapy w środku** — struktura z polem `map[string]int` wymaga inicjalizacji, bo zapis do mapy `nil` panikuje. To najczęstszy powód, dla którego konstruktor jednak jest potrzebny.


## Notatki tutora
- **Eksperyment 3 jest najważniejszy.** Uczeń bez doświadczenia z dziedziczeniem nie ma czego oduczać — ale nauczy się od razu poprawnego modelu, zamiast oczekiwać, że Go zachowa się jak języki obiektowe.
- **Zasada "użyteczna wartość zerowa"** jest jedną z ładniejszych idei Go. Warto ją nazwać, bo tłumaczy, czemu w Go tak rzadko widuje się konstruktory.
- Nie tłumacz wzorców projektowych (kompozycja vs dziedziczenie) w kategoriach teoretycznych. Uczeń nie zna kontekstu tej dyskusji.
- Jeśli uczeń pyta o "interfejsy" po eksperymencie 3 — świetnie, to naturalne wejście w moduł 8. Powiedz: "właśnie tego brakuje, następna lekcja".
