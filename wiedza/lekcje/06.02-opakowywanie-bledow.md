# Lekcja 6.2 — Opakowywanie i rozpoznawanie błędów

## Cel
Po lekcji uczeń:
- Dodaje kontekst do błędu przez `fmt.Errorf` z `%w`
- Rozpoznaje konkretny błąd przez `errors.Is`
- Deklaruje własne błędy jako zmienne (`sentinel errors`)
- Wie, do czego służy `errors.As` i kiedy go szukać

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Dzwoni serwis samochodowy: 'nie da się naprawić'. Co chcesz usłyszeć zamiast tego?"

**Co chcesz usłyszeć:** czego nie da się naprawić, dlaczego, na jakim etapie.

**Drugie pytanie:**
> "Trzy osoby przekazują tę wiadomość: mechanik → recepcja → ty. Czy chcesz, żeby każda z nich **dopisała** swój kawałek kontekstu, czy żeby zastąpiła to, co usłyszała, własnym streszczeniem?"

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Błąd z lekcji 6.1 wędruje w górę przez kolejne funkcje. Każda może **dopisać** swój kawałek kontekstu, nie gubiąc oryginału. Służy do tego `fmt.Errorf` ze znacznikiem `%w`."

Uczeń tworzy `kurs/zadania/17-bledy2/main.go`:

```go
package main

import (
	"errors"
	"fmt"
	"strconv"
)

func wczytajWiek(tekst string) (int, error) {
	n, err := strconv.Atoi(tekst)
	if err != nil {
		return 0, fmt.Errorf("wczytywanie wieku: %w", err)
	}
	return n, nil
}

func main() {
	_, err := wczytajWiek("abc")
	fmt.Println(err)
}
```

→ `wczytywanie wieku: strconv.Atoi: parsing "abc": invalid syntax`

**Pytania:**
- "Ile warstw kontekstu widzisz w tym jednym zdaniu?" → trzy: nasza funkcja, `Atoi`, sam problem
- "Czym różni się `%w` od `%v`?" → `%v` wstawia tekst; `%w` **zachowuje oryginalny błąd w środku**, żeby dało się go później rozpoznać
- "Czy widzisz różnicę w wypisanym tekście?" → nie, wygląda tak samo. Różnica ujawni się za chwilę.

## Krok 3 — Eksperyment (15 min)

1. **`errors.Is` — rozpoznanie błędu w środku opakowania:**
   ```go
   _, err := wczytajWiek("abc")
   fmt.Println(errors.Is(err, strconv.ErrSyntax))   // true
   ```
   > "Nasz błąd jest opakowany, ale `errors.Is` zajrzał do środka. Zmień `%w` na `%v` i sprawdź ponownie."
   → `false`. **To jest cała różnica między `%w` a `%v`.**
2. **Własne błędy jako zmienne (sentinel):**
   ```go
   var (
       ErrPustaLista  = errors.New("lista jest pusta")
       ErrZaDuzoDanych = errors.New("za dużo elementów")
   )

   func srednia(l []int) (float64, error) {
       if len(l) == 0 {
           return 0, ErrPustaLista
       }
       ...
   }

   func main() {
       _, err := srednia(nil)
       if errors.Is(err, ErrPustaLista) {
           fmt.Println("obsługuję pustą listę po swojemu")
       }
   }
   ```
   > "Czemu `Err` z wielkiej litery?" → konwencja Go: nazwy błędów zaczynają się od `Err`, a wielka litera oznacza widoczność z innych pakietów (5.3)
   > "Czemu porównujemy przez `errors.Is`, a nie `err == ErrPustaLista`?" → bo `==` przestanie działać, gdy ktoś po drodze opakuje błąd
3. **Łańcuch przez trzy funkcje** — uczeń pisze:
   ```go
   func poziom3() error { return ErrPustaLista }
   func poziom2() error {
       if err := poziom3(); err != nil {
           return fmt.Errorf("poziom2: %w", err)
       }
       return nil
   }
   func poziom1() error {
       if err := poziom2(); err != nil {
           return fmt.Errorf("poziom1: %w", err)
       }
       return nil
   }

   func main() {
       err := poziom1()
       fmt.Println(err)                           // poziom1: poziom2: lista jest pusta
       fmt.Println(errors.Is(err, ErrPustaLista)) // true
       fmt.Println(errors.Unwrap(err))            // poziom2: lista jest pusta
   }
   ```
   > "Trzy warstwy, a oryginał wciąż rozpoznawalny. Do czego to się przyda w prawdziwym programie?"
4. **Błąd z pliku** — prawdziwy przypadek z biblioteki standardowej:
   ```go
   import "os"

   _, err := os.Open("nie-ma-mnie.txt")
   fmt.Println(err)
   fmt.Println(errors.Is(err, os.ErrNotExist))   // true
   ```
   > "To ten sam wzorzec, tylko błąd pochodzi z systemu operacyjnego. `os.ErrNotExist` to sentinel z biblioteki."
5. **`errors.Join`** — kilka błędów naraz:
   ```go
   var bledy error
   if wiek < 0 {
       bledy = errors.Join(bledy, errors.New("wiek ujemny"))
   }
   if imie == "" {
       bledy = errors.Join(bledy, errors.New("brak imienia"))
   }
   if bledy != nil {
       fmt.Println(bledy)
   }
   ```
   > "Kiedy chcesz **wszystkie** problemy naraz, a nie tylko pierwszy?" → walidacja formularza

## Krok 4 — Pogłębienie (10 min)

**Kiedy opakowywać, a kiedy nie:**
| Sytuacja | Co zrobić |
| --- | --- |
| Przekazujesz błąd wyżej z funkcji, która wie coś więcej | `fmt.Errorf("co robiłem: %w", err)` |
| Błąd sam w sobie jest wystarczająco opisowy | `return err` bez zdobień |
| Nie chcesz, by ktoś rozpoznawał wnętrze (ukrywasz szczegóły) | `%v` zamiast `%w` |
| Tworzysz nowy błąd, niezwiązany z niczym | `errors.New(...)` |

**Nie powtarzaj słowa "błąd"** — komunikat `błąd: błąd: błąd: plik nie istnieje` powstaje, gdy każda warstwa dopisuje "błąd". Dopisuj **czynność**: `wczytywanie konfiguracji: otwieranie pliku: plik nie istnieje`.

**`errors.As` — gdy potrzebujesz szczegółów, nie tożsamości:**
```go
var pathErr *os.PathError
if errors.As(err, &pathErr) {
	fmt.Println("problem z plikiem:", pathErr.Path)
}
```
> "`errors.Is` odpowiada: *czy to ten błąd?*. `errors.As` odpowiada: *czy to błąd tego rodzaju — jeśli tak, daj mi go w całości, wraz z jego polami*."
Pełne zrozumienie wymaga struktur (moduł 7) i interfejsów (8). Tutaj wystarczy, że uczeń rozpozna zapis w cudzym kodzie.

**Własny typ błędu** — zapowiedź modułu 7:
```go
type BladWalidacji struct {
	Pole   string
	Powod  string
}

func (b *BladWalidacji) Error() string {
	return fmt.Sprintf("pole %s: %s", b.Pole, b.Powod)
}
```
> "Cokolwiek ma metodę `Error() string`, jest błędem. Wrócimy do tego, gdy poznasz struktury i metody."

## Pułapki
- **`%v` zamiast `%w`** — tekst wygląda identycznie, ale `errors.Is` przestaje działać. Najbardziej podstępna pułapka tej lekcji: nic nie krzyczy, po prostu przestaje działać rozpoznawanie.
- **`err == ErrCos` zamiast `errors.Is`** — działa, dopóki nikt nie opakuje błędu. Potem cicho przestaje.
- **Opakowywanie w kółko, w każdej funkcji** — daje komunikaty na trzy linijki. Dopisuj kontekst tylko tam, gdzie faktycznie coś wnosisz.
- **Wielkie litery i kropki w komunikacie** — `errors.New("Błąd.")` w środku łańcucha wygląda źle. Konwencja: mała litera, bez kropki.
- **`errors.Join(nil, nil)`** zwraca `nil` — to celowe i wygodne (wzorzec z eksperymentu 5 działa).
- **`errors.As` wymaga wskaźnika na zmienną** (`&pathErr`) — bez `&` dostaniesz panikę. Wskaźniki dopiero w 7.2, więc na tym etapie uczeń tylko rozpoznaje zapis.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`errors.Join`** (1.20) — łączenie wielu błędów w jeden.
- **`errors.AsType[T](err)`** (1.26) — nowsza, bezpieczniejsza forma `errors.As`, bez potrzeby deklarowania zmiennej i brania na nią wskaźnika:
  ```go
  if pe, ok := errors.AsType[*os.PathError](err); ok {
      fmt.Println(pe.Path)
  }
  ```
  Warto pokazać na końcu — jest znacznie czytelniejsza dla początkującego.
- Idiom `%w` istnieje od 1.13 i jest dziś standardem. Kod sprzed 2019 używa `%v` albo bibliotek zewnętrznych (`pkg/errors`) — jeśli uczeń trafi na `errors.Wrap`, to właśnie ta stara droga.

## Notatki tutora
- **Eksperyment 1 (`%w` vs `%v`) jest sercem lekcji.** Uczeń musi zobaczyć `true` zmieniające się w `false` po zmianie jednej litery.
- **Nie wchodź głęboko w `errors.As`.** Bez struktur i interfejsów to tylko zapis do rozpoznania. Pełne omówienie w module 8, jeśli uczeń będzie chciał.
- Jeśli uczeń pyta "kiedy używa się sentineli, a kiedy własnych typów" — odpowiedź praktyczna: sentinel, gdy wystarczy *co się stało*; własny typ, gdy potrzebujesz *szczegółów* (które pole, jaka wartość).
- Ta lekcja jest bardziej "warsztatowa" niż konceptualna. Jeśli uczeń jest zmęczony po module 5 — można ją skrócić do eksperymentów 1-3 i wrócić do reszty przy module 9 (pliki), gdzie błędy pojawią się naturalnie.
