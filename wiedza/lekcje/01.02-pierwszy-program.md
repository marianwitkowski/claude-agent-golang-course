# Lekcja 1.2 — Pierwszy program

## Cel
Po lekcji uczeń:
- Ma własny działający program w Go, napisany od zera
- Wie, co robi każda z pięciu linii `hello.go` i potrafi to powiedzieć swoimi słowami
- Rozróżnia `go run` (uruchom teraz) i `go build` (zrób plik)
- Przeczytał swój pierwszy komunikat błędu kompilatora i sam go naprawił

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Gdy dzwonisz do urzędu, słyszysz: 'wydział X, pokój 12, mówi Kowalski'. Po co ta cała formułka, skoro chodzi tylko o jedno zdanie sprawy?"

**Co chcesz usłyszeć:** żeby wiadomo było, gdzie jesteśmy i kto mówi — kontekst przed treścią.

**Drugie pytanie:**
> "A gdyby wszystkie telefony w urzędzie zaczynały się dokładnie tą samą formułką, w tej samej kolejności — byłoby lepiej czy gorzej?"

(oczekiwane: lepiej — wiadomo, czego się spodziewać)

**Czego NIE rób:** nie mów jeszcze "pakiet", "funkcja", "import".

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Każdy program w Go zaczyna się taką formułką. Zawsze tą samą, zawsze w tej kolejności. Zobacz."

**Uczeń tworzy plik.** Krok po kroku, uczeń wykonuje sam:

```sh
cd kurs/zadania
mkdir 01-hello
```

Uczeń tworzy w edytorze plik `kurs/zadania/01-hello/main.go` i przepisuje **ręcznie** (nie kopiuj-wklej — palce mają zapamiętać):

```go
package main

import "fmt"

func main() {
	fmt.Println("Cześć, tu Go!")
}
```

Uruchomienie — uczeń w terminalu, w katalogu `kurs/zadania`:

```sh
go run ./01-hello
```

**Zapytaj:** "Co się wypisało?"

Dopiero **po** zobaczeniu działania — rozbierzcie kod. Pytaj linia po linii, nie wykładaj:

| Linia | Pytanie do ucznia | Co ma wyjść |
| --- | --- | --- |
| `package main` | "To pierwsza linia każdego programu. Zgadujesz, co znaczy słowo `main`?" | główny, ten do uruchomienia |
| `import "fmt"` | "`fmt` to skrót od `format`. Co program musiał 'przynieść z zewnątrz', żeby coś wypisać?" | gotowe narzędzie do wypisywania |
| `func main()` | "Skąd Go wie, od której linii zacząć wykonywanie?" | od `main` — to punkt wejścia |
| `fmt.Println(...)` | "Co jest przed kropką, a co po?" | pakiet `fmt`, w nim funkcja `Println` |
| `{` i `}` | "Po co te klamry?" | wyznaczają, co należy do funkcji |

Teraz nazwij rzeczy: **pakiet**, **import**, **funkcja**, **punkt wejścia**.

## Krok 3 — Eksperyment (15 min)
Uczeń modyfikuje swój plik i za każdym razem uruchamia `go run ./01-hello`. **Uczeń uruchamia sam, agent nie uruchamia.**

1. Zmień tekst w cudzysłowie na własne imię. Uruchom.
2. Dodaj **drugą** linię `fmt.Println("...")` pod pierwszą. Uruchom. W jakiej kolejności się wypisały?
3. Zamień kolejność obu linii `fmt.Println`. Uruchom. Co to mówi o tym, jak Go czyta program?
4. **Zepsuj celowo:** usuń linię `import "fmt"`. Uruchom.
   → **Zapytaj: "Wklej mi dokładnie, co powiedział kompilator."**
   Komunikat: `undefined: fmt`
   > "Co Go próbuje ci powiedzieć tym słowem `undefined`?"
5. Przywróć import. Teraz zmień `Println` na `println` (małą literą). Uruchom.
   → Program zadziała, ale inaczej (`println` to wbudowana funkcja diagnostyczna, wypisuje na inne wyjście).
   > "Wielkość liter ma znaczenie w Go. To będzie ważne w module 5 — zapamiętaj to uczucie."
6. Zmień `func main()` na `func start()`. Uruchom.
   → `function main is undeclared in the main package`
   > "Co się stało? Czy Go potrafi zgadnąć, że `start` to twój początek?"

**Po każdym błędzie pytaj:** "Która część komunikatu wskazuje **gdzie** jest problem, a która **co** jest problemem?"

## Krok 4 — Pogłębienie (10 min)

**`go run` vs `go build`** — uczeń wykonuje oba:

```sh
go run ./01-hello       # kompiluje do pamięci i od razu uruchamia; nic nie zostaje
go build ./01-hello     # kompiluje i zostawia plik `01-hello` w bieżącym katalogu
ls                      # uczeń widzi nowy plik
./01-hello              # uruchomienie gotowej binarki (Windows: .\01-hello.exe)
```

**Pytania:**
- "Czym różni się to, co widzisz po `go run`, od tego po `go build`?"
- "Gdybyś chciał wysłać program koledze, który **nie ma zainstalowanego Go** — co mu wyślesz?"
- "Sprawdź rozmiar tej binarki (`ls -lh`). Dlaczego ~2 MB, skoro kod ma 5 linijek?"
  → bo w środku jest wszystko, czego program potrzebuje. Dlatego działa bez instalowania czegokolwiek.

Po eksperymencie uczeń **kasuje binarkę** (`rm 01-hello`) — nie zaśmiecamy repozytorium.

**Kolejne "co jeśli":**
- "Co się stanie, jeśli w jednym katalogu będą dwa pliki `.go`, oba z `func main()`?" → niech spróbuje. `main redeclared in this block`.
- "A jeśli w środku `main` nie będzie nic?" → program się uruchomi i natychmiast skończy. To poprawny program.

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "pierwszy program". Sugerowane:
- 🔥 Program wypisujący trzy linie: imię, miasto, ulubione danie
- ⭐ Program "wizytówka": wypisuje ramkę z gwiazdek, w środku dane (same `Println`, jeszcze bez zmiennych)
- ⚡ Zepsuj własny program na 3 różne sposoby, za każdym razem zapisz komunikat błędu i co znaczy

Kod ucznia: `kurs/zadania/01-hello/` lub nowy podkatalog.

## Pułapki
- **Klamra `{` musi być w tej samej linii co `func main()`.** Przeniesiona do następnej linii = błąd składni. To nie jest kwestia stylu — Go automatycznie wstawia średniki na końcu linii i przeniesiona klamra psuje program. Uczeń może to sprowokować i zobaczyć.
- **`go run ./01-hello` vs `go run main.go`** — obie formy działają, ale ta pierwsza (katalog) jest tą, której uczymy: działa też, gdy program urośnie do kilku plików.
- **Uruchamianie z niewłaściwego katalogu** — najczęstszy problem pierwszej lekcji. Uczeń musi być w `kurs/zadania`. Sprawdzenie: `pwd`.
- **Nieużywany import to błąd, nie ostrzeżenie.** Dodaj `import "os"` i nie użyj → `"os" imported and not used`. Go jest tu bezlitosny i to celowe.
- **Windows** — binarka nazywa się `01-hello.exe`, uruchamiana `.\01-hello.exe`.

## Notatki tutora
- **Przepisywanie ręczne jest ważne.** Jeśli uczeń wkleja kod, tracisz połowę wartości lekcji — literówki i błędy składni są tu materiałem dydaktycznym, nie przeszkodą.
- Jeśli uczeń pyta "po co `fmt`, czemu nie po prostu `print`" — odpowiedz krótko: "bo Go trzyma w rdzeniu tylko minimum, reszta to pakiety, które bierzesz gdy potrzebujesz". Nie rozwijaj.
- **Nie wprowadzaj zmiennych.** Uczeń może zapytać "a jak wypisać wynik dodawania" — odpowiedz "następna lekcja o formatowaniu, a zmienne w 2.1".
- Gdy uczeń zobaczy pierwszy komunikat błędu, może się przestraszyć. Powiedz wprost: **"Kompilator jest twoim recenzentem, nie wrogiem. Lepiej, że mówi teraz, niż żeby program się wysypał u użytkownika."** To zdanie warto powtórzyć w module 6.
