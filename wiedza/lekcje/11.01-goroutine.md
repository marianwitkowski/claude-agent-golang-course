# Lekcja 11.1 — Goroutine

## Cel
Po lekcji uczeń:
- Uruchamia funkcję "obok" przez słowo `go`
- Rozumie, dlaczego program kończy się, nie czekając na goroutine
- Używa `sync.WaitGroup` do poczekania na zakończenie
- Wie, kiedy współbieżność pomaga, a kiedy jest zbędna

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Gotujesz obiad: woda na makaron wrze 10 minut, sos smaży się 8 minut. Robisz to po kolei czy równolegle? Ile czasu zajmie każda wersja?"

**Drugie pytanie:**
> "A jeśli przepis wymaga, żeby najpierw ugotować makaron, **potem** wrzucić go na patelnię — czy równoległość coś da?"

→ nie zawsze. Równolegle da się tylko to, co od siebie nie zależy.

**Trzecie:**
> "Czekasz na dostawę i na telefon od lekarza. Czy stanie pod drzwiami przyspieszy telefon?"

→ czekanie na kilka rzeczy naraz to główny powód, dla którego współbieżność ma sens.

## Krok 2 — Mostek (10 min)
**Mostek:**
> "W Go dopisujesz jedno słowo — `go` — przed wywołaniem funkcji, i ona zaczyna działać obok. To się nazywa **goroutine**."

Uczeń tworzy `kurs/zadania/30-goroutine/main.go`:

```go
package main

import (
	"fmt"
	"time"
)

func gotuj(co string, sekundy int) {
	for i := 1; i <= sekundy; i++ {
		fmt.Printf("%s: minuta %d\n", co, i)
		time.Sleep(100 * time.Millisecond)
	}
	fmt.Println(co, "gotowe")
}

func main() {
	gotuj("makaron", 3)
	gotuj("sos", 3)
	fmt.Println("obiad podany")
}
```

Uczeń uruchamia (po kolei), potem zmienia na:
```go
	go gotuj("makaron", 3)
	go gotuj("sos", 3)
	fmt.Println("obiad podany")
```

**Pytania:**
- "Co się wypisało za drugim razem?" → prawdopodobnie **tylko** "obiad podany"
- "Gdzie się podziało gotowanie?" → `main` skończył się i zabrał ze sobą cały program
- "Wróć do analogii: co zrobiłeś nie tak w kuchni?" → wyszedłeś z domu, nie czekając

## Krok 3 — Eksperyment (15-20 min)

1. **Naiwna naprawa — `Sleep`:**
   ```go
   go gotuj("makaron", 3)
   go gotuj("sos", 3)
   time.Sleep(1 * time.Second)
   fmt.Println("obiad podany")
   ```
   > "Zadziałało. Ale co, jeśli makaron będzie się gotował dłużej, niż zgadłeś?"
   → **`Sleep` to nie jest synchronizacja**, tylko zgadywanie. Nigdy tak nie rób w prawdziwym programie.
2. **`sync.WaitGroup` — poprawnie:**
   ```go
   import "sync"

   func main() {
       var wg sync.WaitGroup

       wg.Add(1)
       go func() {
           defer wg.Done()
           gotuj("makaron", 3)
       }()

       wg.Add(1)
       go func() {
           defer wg.Done()
           gotuj("sos", 3)
       }()

       wg.Wait()
       fmt.Println("obiad podany")
   }
   ```
   > "Trzy metody: `Add`, `Done`, `Wait`. Co liczy `WaitGroup`?" → ile zadań jest w toku
   > "Czemu `defer wg.Done()`, a nie zwykłe wywołanie na końcu?" → z 5.3: wykona się nawet przy panice
   > "Co się stanie, jeśli usuniesz jedno `wg.Add(1)`?" → `Wait` zwolni za wcześnie
   > "A jeśli usuniesz `wg.Done()`?" → `fatal error: all goroutines are asleep - deadlock!` — program czeka w nieskończoność
3. **Wiele goroutine w pętli:**
   ```go
   var wg sync.WaitGroup
   dania := []string{"makaron", "sos", "sałatka", "deser"}

   for _, d := range dania {
       wg.Add(1)
       go func() {
           defer wg.Done()
           gotuj(d, 2)
       }()
   }
   wg.Wait()
   ```
   > "Uruchom kilka razy. Czy kolejność wypisywania jest zawsze taka sama?"
   → nie. **Kolejność wykonania goroutine jest nieprzewidywalna.**
   > "Uwaga historyczna: przed Go 1.22 ten kod byłby błędny — wszystkie goroutine widziałyby tę samą zmienną `d` i gotowałyby cztery razy deser. Pamiętasz zmienną pętli z 3.3 i 5.2? Oto konsekwencja."
4. **Ile ich można?**
   ```go
   var wg sync.WaitGroup
   for i := range 10000 {
       wg.Add(1)
       go func() {
           defer wg.Done()
           _ = i * i
       }()
   }
   wg.Wait()
   fmt.Println("gotowe")
   ```
   > "Dziesięć tysięcy równoległych zadań i program nawet nie mrugnął. Goroutine kosztuje kilka kilobajtów — wątek systemowy kosztuje megabajt. Stąd popularność Go do serwerów."
5. **Panika w goroutine** — ważne ostrzeżenie:
   ```go
   go func() {
       panic("coś padło")
   }()
   time.Sleep(time.Second)
   ```
   > "Cały program pada. `recover` w `main` **tego nie złapie** (6.3) — musi być wewnątrz tej goroutine."

## Krok 4 — Pogłębienie (10 min)

**Kiedy współbieżność ma sens:**
| Zadanie | Pomoże? |
| --- | --- |
| Pobranie 50 stron internetowych | tak, ogromnie — czekasz na sieć |
| Odczyt 100 plików | tak, umiarkowanie |
| Zsumowanie miliona liczb w pamięci | rzadko — koszt koordynacji zjada zysk |
| Program, który i tak czeka na użytkownika | nie |

> "Współbieżność najbardziej pomaga, gdy program **czeka** — na sieć, dysk, użytkownika. Przy czystym liczeniu zysk jest mniejszy i trudniejszy."

**Współbieżność to nie to samo co równoległość:**
- **współbieżność** — kilka zadań w toku naraz (Go daje strukturę do tego)
- **równoległość** — kilka zadań wykonywanych fizycznie jednocześnie na kilku rdzeniach

> "Jeden kelner obsługujący pięć stolików działa współbieżnie, ale nie równolegle. Pięciu kelnerów — równolegle."

**Jak przekazać wynik z goroutine?**
```go
// var wynik int
// go func() { wynik = policz() }()     // NIEBEZPIECZNE — wyścig
```
> "Dwie goroutine dotykające tej samej zmiennej to **wyścig danych**. Rozwiązanie: kanały (11.2) albo mutex (11.3)."

**`go` na metodzie i z argumentami:**
```go
go obiekt.Metoda()
go func(x int) { fmt.Println(x) }(42)
```

**Nie zostawiaj goroutine bez końca** — goroutine czekająca w nieskończoność to wyciek. W 11.2 i 11.3 uczeń pozna sposoby na porządne kończenie.

## Pułapki
- **`main` kończy się i zabija goroutine** — pierwszy i najczęstszy problem. Objaw: program nic nie wypisuje.
- **`time.Sleep` zamiast synchronizacji** — działa na twoim komputerze, psuje się na wolniejszym.
- **Brak `wg.Done()`** → zakleszczenie (`deadlock`). Go to wykrywa i mówi wprost.
- **`wg.Add` wewnątrz goroutine** — `Wait` może wystartować, zanim licznik urośnie. `Add` **przed** `go`.
- **Wspólna zmienna bez ochrony** → wyścig danych; wyniki losowe i niepowtarzalne. Wykrywanie: `go test -race` albo `go run -race` (11.3).
- **Panika w goroutine zabija cały program** — `recover` musi być w tej samej goroutine.
- **Goroutine, która nigdy się nie kończy** — wyciek. Widoczny dopiero w programie działającym godzinami.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`wg.Go(func(){...})`** (1.25) zastępuje rytuał `Add`/`go`/`defer Done`:
  ```go
  var wg sync.WaitGroup
  wg.Go(func() { gotuj("makaron", 3) })
  wg.Go(func() { gotuj("sos", 3) })
  wg.Wait()
  ```
  **Pokaż dopiero po eksperymencie 2** — uczeń musi najpierw rozumieć, co liczą `Add` i `Done`.
- **Zmienna pętli nowa w każdym obiegu** (1.22) — usunęła klasyczny błąd początkujących z eksperymentu 3. Starsze tutoriale każą pisać `go func(d string){...}(d)`; dziś to zbędne.
- **`GOMAXPROCS` respektuje limity kontenera** (1.25) — wyjaśnia różnice wydajności w Dockerze.

## Notatki tutora
- **Trzymaj poziom "łagodny".** Cel: uczeń rozumie, co robi `go` i `WaitGroup`, i wie, że wspólne dane są niebezpieczne. Model pamięci, `context`, wzorce puli zadań — poza kursem.
- **Eksperyment 1 (`main` kończy program) jest obowiązkowy** — bez niego `WaitGroup` wygląda na zbędny rytuał.
- **Nie pokazuj `wg.Go` przed `Add`/`Done`.** Skrót bez zrozumienia mechanizmu psuje intuicję.
- Analogia kuchenna działa świetnie na całą lekcję — warto ją utrzymać także w 11.2 (kanał = okienko podawcze).
- Jeśli uczeń jest zafascynowany i chce budować coś współbieżnego w projekcie z modułu 12 — ostrzeż, że współbieżność podwaja trudność debugowania. Zaproponuj wersję sekwencyjną najpierw.
