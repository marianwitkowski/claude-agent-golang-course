# Lekcja 6.1 — `error` to zwykła wartość

## Cel
Po lekcji uczeń:
- Czyta i pisze wzorzec `wynik, err := ...` + `if err != nil`
- Tworzy własny błąd przez `errors.New`
- Rozumie, czym jest `nil` w kontekście błędu
- Pisze funkcję zwracającą `(wynik, error)` i obsługuje ją poprawnie

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Zamawiasz paczkę. Kurier przychodzi i mówi: 'nie zastałem, paczka wróciła'. Albo: podrzuca awizo do skrzynki i idzie dalej, a ty dowiadujesz się za tydzień. Który sposób wolisz?"

**Drugie pytanie:**
> "A trzeci wariant: kurier nie mówi nic, tylko po prostu nie ma paczki. Skąd się dowiesz, że coś poszło nie tak?"

**Co chcesz usłyszeć:** najlepiej dowiedzieć się od razu, przy odbiorze, wprost.

## Krok 2 — Mostek (10 min)
**Mostek:**
> "W wielu językach błąd jest jak awizo — leci gdzieś w górę i ktoś go kiedyś złapie, albo i nie. Go robi to inaczej: funkcja **zwraca błąd jako drugą wartość**, tak jak zwraca wynik. Nie da się go nie zauważyć, bo stoi w tej samej linii."

Uczeń tworzy `kurs/zadania/16-bledy/main.go`:

```go
package main

import (
	"errors"
	"fmt"
)

func podziel(a, b float64) (float64, error) {
	if b == 0 {
		return 0, errors.New("nie można dzielić przez zero")
	}
	return a / b, nil
}

func main() {
	wynik, err := podziel(10, 2)
	if err != nil {
		fmt.Println("błąd:", err)
		return
	}
	fmt.Println("wynik:", wynik)
}
```

**Pytania:**
- "Porównaj z funkcją `podziel` z lekcji 5.1, która zwracała `(int, bool)`. Co się zmieniło?" → zamiast `bool` mamy `error`, który **niesie komunikat**
- "Co zwracamy, gdy wszystko poszło dobrze?" → `nil`, czyli "żadnego błędu"
- "Zmień wywołanie na `podziel(10, 0)` i uruchom."

**Nazwij `nil`:** to "brak wartości", "nic tu nie ma". Uczeń widział je już przy pustym slice (4.1) i mapie (4.3).

## Krok 3 — Eksperyment (15-20 min)

1. **`err` to wartość jak każda inna:**
   ```go
   _, err := podziel(1, 0)
   fmt.Printf("%T\n", err)      // *errors.errorString
   fmt.Println(err.Error())     // ten sam tekst co przy Println
   ```
   > "`err` ma typ i metodę. To zwykła wartość, nie żadna magia."
2. **Wzorzec: sprawdź i wyjdź:**
   ```go
   wynik, err := podziel(10, 0)
   if err != nil {
       fmt.Println("błąd:", err)
       return
   }
   fmt.Println(wynik)
   ```
   > "Pamiętasz 'wczesne wyjście' z 3.1? To jest jego najważniejsze zastosowanie."
   > "Co jest w `wynik`, gdy wystąpił błąd?" → `0`, bo tak napisaliśmy funkcję. **Przy błędzie nie ufaj pierwszej wartości.**
3. **Ignorowanie błędu — pokaż, dlaczego to złe:**
   ```go
   wynik, _ := podziel(10, 0)
   fmt.Println(wynik)   // 0 — wygląda jak prawidłowy wynik dzielenia
   ```
   > "Program działa, nikt nie krzyczy, a wynik jest fałszywy. Kiedy się o tym dowiesz?"
4. **Prawdziwy błąd z biblioteki** — uczeń wraca do `strconv.Atoi` z 2.4:
   ```go
   n, err := strconv.Atoi("abc")
   fmt.Println(n, err)
   ```
   → `0 strconv.Atoi: parsing "abc": invalid syntax`
   > "Zobacz, co jest w komunikacie: która funkcja, jakie dane, co dokładnie źle. Dobry błąd odpowiada na te trzy pytania."
5. **Łańcuch wywołań** — uczeń pisze funkcję używającą innej funkcji zwracającej błąd:
   ```go
   func sredniaZTekstow(teksty []string) (float64, error) {
       suma := 0
       for _, t := range teksty {
           n, err := strconv.Atoi(t)
           if err != nil {
               return 0, err          // przekazujemy błąd wyżej
           }
           suma += n
       }
       if len(teksty) == 0 {
           return 0, errors.New("pusta lista")
       }
       return float64(suma) / float64(len(teksty)), nil
   }
   ```
   > "Co robi `return 0, err` w środku pętli?" → przerywa i oddaje problem temu, kto wywołał
   Uczeń testuje na `[]string{"1","2","x"}` i na pustej liście.
6. **Funkcja zwracająca tylko błąd:**
   ```go
   func sprawdzWiek(w int) error {
       if w < 0 {
           return errors.New("wiek ujemny")
       }
       if w > 150 {
           return errors.New("wiek nierealny")
       }
       return nil
   }

   if err := sprawdzWiek(200); err != nil {
       fmt.Println(err)
   }
   ```
   > "Zwróć uwagę na zapis `if err := ...; err != nil` — instrukcja inicjująca z 3.1. To najczęstsza linia w kodzie Go."

## Krok 4 — Pogłębienie (10 min)

**Czym właściwie jest `error`?**
```go
type error interface {
	Error() string
}
```
> "To **interfejs** — czyli wymaganie: 'cokolwiek potrafi zwrócić swój opis tekstem, może być błędem'. Interfejsami zajmiemy się w module 8. Na razie: `error` to coś, co umie się opisać."

**Dobre komunikaty błędów — konwencje Go:**
- małą literą, bez kropki na końcu: `errors.New("nie można otworzyć pliku")`, nie `"Nie można otworzyć pliku."`
- powód: błędy są **sklejane** w łańcuchy (`otwieranie konfiguracji: nie można otworzyć pliku`), a wielkie litery i kropki w środku zdania wyglądają źle
- konkret zamiast ogólników: nie "błąd", tylko co i dlaczego

**Porównanie z wyjątkami** — uczeń może o to zapytać:
| Wyjątki (inne języki) | Błędy jako wartości (Go) |
| --- | --- |
| Wyjątek leci w górę sam | Błąd trzeba przekazać jawnie |
| Kod główny jest krótszy | Kodu jest więcej |
| Łatwo przeoczyć, co może rzucić | W sygnaturze widać, że może się nie udać |
| Obsługa daleko od miejsca błędu | Obsługa tuż obok |

> "Który sposób ci się podoba? Nie ma złej odpowiedzi — Go wybrał ten drugi i konsekwentnie się go trzyma."

**`panic` to co innego** — jedno zdanie zapowiedzi: `panic` zatrzymuje program i jest zarezerwowany dla sytuacji, w których dalsze działanie nie ma sensu. Temat 6.3.

## Krok 5 — Ćwiczenie
→ Skill `cwiczenie`. Temat: "błędy jako wartości". Sugerowane:
- 🔥 Funkcja `pierwiastek(x float64) (float64, error)` — błąd dla liczb ujemnych (użyj `math.Sqrt`)
- ⭐ Funkcja `wczytajWiek(tekst string) (int, error)` — zamienia tekst na liczbę i sprawdza zakres 0-150; obsłuż oba rodzaje błędu osobno
- ⚡ Program pyta użytkownika o liczby aż do pustej linii, sumuje je; przy błędnym wpisie wypisuje komunikat i **pyta dalej** zamiast kończyć

Kod ucznia: `kurs/zadania/16-bledy/`.

## Pułapki
- **Ignorowanie `err` przez `_`** — kompiluje się, jest legalne i jest najczęstszym grzechem początkującego. Zasada kursu: **jeśli funkcja zwraca `err`, sprawdzasz go.**
- **Użycie wyniku mimo błędu** — przy `err != nil` pierwsza wartość jest zwykle bezużyteczna.
- **`if err == nil` zamiast `!= nil`** — odwrócona logika, kod wchodzi w gałąź błędu tylko przy sukcesie. Czytaj `!= nil` jako "coś poszło nie tak".
- **Przesłanianie `err`** (z 5.3): `if n, err := f(); err != nil { }` tworzy **nowe** `err` w zasięgu `if`. Zewnętrzne `err` zostaje nietknięte. Klasyczne źródło "czemu ten błąd zniknął".
- **Zwracanie `nil` jako wyniku i `nil` jako błędu jednocześnie** — sygnał, że funkcja nie ma jasno określonego kontraktu.
- **`errors.New` w pętli** — tworzy nowy obiekt za każdym razem. Nieszkodliwe, ale jeśli błąd jest stały, lepiej zadeklarować go raz jako zmienną pakietową (6.2).

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- Idiom `if err != nil` jest niezmieniony od Go 1.0 i nie zapowiada się na zmianę. Propozycje skróconej składni (`try`, `?`) były odrzucane wielokrotnie.
- Nowsze narzędzia (`errors.Is`, `%w`, `errors.Join`, `errors.AsType`) rozszerzają ten wzorzec, nie zastępują go. Wszystkie w 6.2.

## Notatki tutora
- **To najważniejsza lekcja w całym kursie po module 3.** Uczeń będzie pisał `if err != nil` codziennie przez resztę życia z Go.
- Uczeń może narzekać na gadatliwość ("trzy linie na każde wywołanie"). **Nie broń Go teatralnie** — przyznaj, że tak jest, i pokaż, co się dostaje w zamian: nie ma niespodzianek, w sygnaturze widać, co może się nie udać.
- **Nie tłumacz interfejsów.** "Error to coś, co umie się opisać tekstem" wystarczy do modułu 8.
- Jeśli uczeń zna wyjątki z innego języka i pyta "czemu bez `try`" — tabela z kroku 4 wystarczy. Nie prowadź debaty.
- Warto połączyć z 2.4: uczeń użył `err` w drugiej lekcji kursu, nie rozumiejąc. Teraz rozumie. To dobre poczucie postępu — nazwij je.
