# Lekcja 8.1 — Interfejsy

## Cel
Po lekcji uczeń:
- Definiuje interfejs i pisze funkcję działającą na dowolnym typie, który go spełnia
- Rozumie, że w Go typ spełnia interfejs **automatycznie**, bez deklaracji
- Wie, że interfejs definiuje się tam, gdzie się go **używa**, nie tam, gdzie się go implementuje
- Rozpoznaje, kiedy interfejs pomaga, a kiedy jest zbędnym utrudnieniem

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Gniazdko w ścianie. Co musi mieć urządzenie, żeby z niego skorzystać? Czy gniazdko wie, czy podłączasz lampę, ładowarkę czy odkurzacz?"

**Co chcesz usłyszeć:** musi mieć pasującą wtyczkę. Gniazdko nie wie i nie musi wiedzieć, co jest po drugiej stronie.

**Drugie pytanie:**
> "Producent nowego urządzenia dzwoni do elektrowni, żeby zgłosić, że jego wtyczka pasuje?"

→ nie. Pasuje albo nie pasuje. To wszystko.

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Interfejs to opis wtyczki: lista metod, które coś musi mieć. Każdy typ, który je ma, **automatycznie** pasuje. Nie trzeba niczego zgłaszać."

Uczeń tworzy `kurs/zadania/22-interfejsy/main.go`:

```go
package main

import "fmt"

type Figura interface {
	Pole() float64
	Obwod() float64
}

type Prostokat struct{ Szerokosc, Wysokosc float64 }
type Kolo struct{ Promien float64 }

func (p Prostokat) Pole() float64  { return p.Szerokosc * p.Wysokosc }
func (p Prostokat) Obwod() float64 { return 2 * (p.Szerokosc + p.Wysokosc) }

func (k Kolo) Pole() float64  { return 3.14159 * k.Promien * k.Promien }
func (k Kolo) Obwod() float64 { return 2 * 3.14159 * k.Promien }

func opisz(f Figura) {
	fmt.Printf("pole: %.2f, obwód: %.2f\n", f.Pole(), f.Obwod())
}

func main() {
	opisz(Prostokat{Szerokosc: 3, Wysokosc: 4})
	opisz(Kolo{Promien: 2})
}
```

**Pytania:**
- "Gdzie w kodzie `Prostokat` deklaruje, że jest `Figura`?" → **nigdzie**. Ma obie metody, więc jest.
- "Co przyjmuje funkcja `opisz`?" → cokolwiek, co ma `Pole()` i `Obwod()`
- "Usuń metodę `Obwod` z `Kolo` i skompiluj." → `Kolo does not implement Figura (missing method Obwod)`
- "Kiedy Go to sprawdziło — przy definicji typu czy przy wywołaniu?" → przy próbie użycia

## Krok 3 — Eksperyment (15-20 min)

1. **Slice interfejsów** — najczęstsze zastosowanie:
   ```go
   figury := []Figura{
       Prostokat{Szerokosc: 3, Wysokosc: 4},
       Kolo{Promien: 1},
       Prostokat{Szerokosc: 1, Wysokosc: 1},
   }

   suma := 0.0
   for _, f := range figury {
       suma += f.Pole()
   }
   fmt.Printf("łączne pole: %.2f\n", suma)
   ```
   > "W jednym slice są dwa **różne** typy. Jak to możliwe, skoro slice ma jeden typ elementu (4.1)?"
   → typem elementu jest `Figura`. Konkretny typ jest w środku.
2. **Bez interfejsu** — pokaż, co interfejs zastępuje:
   ```go
   func sumaPolBezInterfejsu(prostokaty []Prostokat, kola []Kolo) float64 {
       // dwie osobne pętle... a przy trzeciej figurze trzecia
   }
   ```
   > "Ile trzeba dopisać przy nowym kształcie w każdej z wersji?"
3. **Wartość zerowa interfejsu:**
   ```go
   var f Figura
   fmt.Println(f == nil)   // true
   // f.Pole()             // panic: nil pointer dereference
   ```
   > "Interfejs bez przypisanej wartości jest `nil`. Znasz to z 7.2."
4. **Interfejs z jedną metodą — najczęstszy w Go:**
   ```go
   type Powitalny interface {
       Przywitaj() string
   }

   type Pies struct{ Imie string }
   func (p Pies) Przywitaj() string { return p.Imie + " szczeka" }

   type Robot struct{ ID int }
   func (r Robot) Przywitaj() string { return fmt.Sprintf("robot %d: bip", r.ID) }

   for _, x := range []Powitalny{Pies{"Burek"}, Robot{7}} {
       fmt.Println(x.Przywitaj())
   }
   ```
   > "Im mniej metod w interfejsie, tym więcej typów go spełnia. Idiom Go: **interfejsy są małe**, często jednometodowe."
5. **Odbiornik wskaźnikowy a interfejs** — pułapka warta zobaczenia:
   ```go
   type Licznik struct{ n int }
   func (l *Licznik) Przywitaj() string { l.n++; return "hej" }

   var p Powitalny = &Licznik{}   // OK — wskaźnik
   // var q Powitalny = Licznik{} // BŁĄD: Licznik does not implement Powitalny
   //                             // (method Przywitaj has pointer receiver)
   ```
   > "Pamiętasz radę z 7.2, żeby nie mieszać odbiorników? Oto powód."
6. **Interfejs, którego uczeń już używał:**
   ```go
   type error interface {
       Error() string
   }
   ```
   > "`error` z modułu 6 to zwykły interfejs z jedną metodą. Nic magicznego."
   Uczeń pisze własny typ błędu — teraz ma wszystkie klocki:
   ```go
   type BladWalidacji struct{ Pole, Powod string }

   func (b *BladWalidacji) Error() string {
       return fmt.Sprintf("pole %s: %s", b.Pole, b.Powod)
   }

   func sprawdz(wiek int) error {
       if wiek < 0 {
           return &BladWalidacji{Pole: "wiek", Powod: "wartość ujemna"}
       }
       return nil
   }
   ```

## Krok 4 — Pogłębienie (10 min)

**Gdzie definiować interfejs?** To najważniejsza zasada tej lekcji:
> "Interfejs definiuje **ten, kto go używa**, nie ten, kto go implementuje."

W innych językach autor biblioteki deklaruje interfejs, a klasy zgłaszają, że go implementują. W Go jest odwrotnie: piszesz funkcję, wypisujesz, czego od argumentu potrzebujesz, i **każdy pasujący typ, także napisany wcześniej i przez kogoś innego, zadziała**.

**Nie definiuj interfejsu "na zapas":**
```go
// ŹLE — interfejs bez drugiego typu i bez potrzeby
type Zapisywacz interface{ Zapisz(s string) error }
type PlikowyZapisywacz struct{}   // jedyna implementacja
```
> "Jedna implementacja i jeden użytkownik? Nie potrzebujesz interfejsu. Dodasz go, gdy pojawi się drugi przypadek."

**`any` — interfejs pusty:**
```go
var cokolwiek any = 42
cokolwiek = "tekst"
cokolwiek = Prostokat{1, 2}
```
> "Interfejs bez metod spełnia **każdy** typ. Wygodne, ale wtedy nie wiadomo, co można z tym zrobić. Do wyjmowania konkretu służy asercja typu — następna lekcja."
`any` to od Go 1.18 alias na `interface{}`. Starszy kod pisze `interface{}` — to to samo.

**Interfejsy z biblioteki standardowej, które uczeń spotka:**
| Interfejs | Metoda | Gdzie |
| --- | --- | --- |
| `error` | `Error() string` | wszędzie (moduł 6) |
| `fmt.Stringer` | `String() string` | wypisywanie (8.2) |
| `io.Writer` | `Write([]byte) (int, error)` | pliki, sieć (moduł 9) |
| `io.Reader` | `Read([]byte) (int, error)` | pliki, sieć (moduł 9) |
| `sort.Interface` | trzy metody | starsze sortowanie |

## Pułapki
- **`does not implement` z powodu odbiornika wskaźnikowego** — najczęstszy błąd. Komunikat mówi wprost: `method has pointer receiver`. Rozwiązanie: przekaż `&wartosc`.
- **Literówka w nazwie metody** — typ po prostu nie spełnia interfejsu, a komunikat wskazuje "brakującą" metodę. Sprawdź wielkość liter.
- **Interfejs `nil` a wskaźnik `nil` w interfejsie** — pułapka dla zaawansowanych: interfejs zawierający wskaźnik `nil` **nie jest** równy `nil`. Wystarczy wzmianka; szczegóły znacznie wykraczają poza kurs.
- **Interfejs na zapas** — jedna implementacja, jeden użytkownik, zero zysku. Częsty nawyk przenoszony z innych języków.
- **Zbyt duże interfejsy** — dziesięciometodowy interfejs spełni jeden typ. Małe są użyteczne.
- **`any` wszędzie** — traci się kontrolę typów, którą Go daje za darmo. `any` tylko wtedy, gdy naprawdę nie wiadomo, co przyjdzie.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`any` zamiast `interface{}`** — pisz `any` (od 1.18). Starsze materiały używają `interface{}`.
- Generyki (od 1.18) rozwiązują część problemów, do których wcześniej używano interfejsów (np. funkcja działająca na dowolnym typie liczbowym). **Poza kursem** — jeśli uczeń zobaczy `func Suma[T int|float64](s []T) T`, powiedz: "to generyki, temat na później".
- Metody z własnymi parametrami typowymi (1.27) — również poza kursem.

## Notatki tutora
- **Motywacja przed mechanizmem.** Eksperyment 2 (wersja bez interfejsu) pokazuje, po co to całe zamieszanie. Bez tego interfejsy wyglądają na komplikację.
- **Niejawna implementacja zaskakuje osoby po innych językach** — ale uczeń bez tego bagażu przyjmie to naturalnie. Nie wprowadzaj porównań, których nie ma w jego głowie.
- **Zasada "interfejs u użytkownika, nie u dostawcy"** jest ważniejsza niż składnia. Warto powtórzyć na końcu lekcji.
- Nie wchodź w wewnętrzną budowę interfejsu (para typ+wartość) ani w pułapkę "typed nil". To wiedza dla zaawansowanych; wspomnij i idź dalej.
- Jeśli uczeń pyta o generyki — powiedz krótko, do czego służą, i że kurs ich nie obejmuje. Nie próbuj wyjaśniać.
