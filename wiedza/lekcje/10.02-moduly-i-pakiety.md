# Lekcja 10.2 — Moduły i pakiety

## Cel
Po lekcji uczeń:
- Zakłada własny moduł przez `go mod init` i rozumie, co jest w `go.mod`
- Dzieli program na pakiety w podkatalogach i importuje własny kod
- Dodaje zależność zewnętrzną i wie, po co jest `go.sum`
- Używa `go mod tidy` do porządkowania zależności

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Przez cały kurs pisałeś w katalogu `kurs/zadania`, w którym leżał plik `go.mod`, o którym nic nie mówiliśmy. Zajrzyj do niego. Co tam jest?"

```
module kurs/zadania

go 1.22
```

**Drugie pytanie:**
> "Twój program ma 500 linii w jednym pliku. Chcesz podzielić go na części tak, żeby część 'obsługa plików' nie miała dostępu do wnętrza części 'obliczenia'. Jak to zrobić?"

## Krok 2 — Mostek (10 min)
**Mostek:**
> "Moduł to **cały projekt** — jedna jednostka z nazwą i wersją. Pakiet to **jeden katalog** wewnątrz. Znasz już pakiety: `fmt`, `os`, `strings` — teraz zrobisz własny."

Uczeń tworzy nowy projekt **poza** katalogiem zadań, żeby zobaczyć pełną strukturę:

```sh
mkdir -p kurs/zadania/28-moduly/kalkulator
cd kurs/zadania/28-moduly
```

Struktura:
```
28-moduly/
├── main.go
└── kalkulator/
    └── kalkulator.go
```

`kalkulator/kalkulator.go`:
```go
package kalkulator

func Dodaj(a, b float64) float64 { return a + b }
func Odejmij(a, b float64) float64 { return a - b }

func wewnetrzna() string { return "niewidoczna z zewnątrz" }
```

`main.go`:
```go
package main

import (
	"fmt"

	"kurs/zadania/28-moduly/kalkulator"
)

func main() {
	fmt.Println(kalkulator.Dodaj(2, 3))
	// fmt.Println(kalkulator.wewnetrzna())   // BŁĄD
}
```

**Pytania:**
- "Skąd wzięła się ścieżka importu `kurs/zadania/28-moduly/kalkulator`?" → nazwa modułu z `go.mod` + ścieżka katalogu
- "Czemu `wewnetrzna()` nie działa z zewnątrz?" → mała litera. Zasada z 5.3, teraz z prawdziwym pakietem.
- "Nazwa pakietu (`package kalkulator`) a nazwa katalogu — muszą być takie same?" → nie muszą, ale **zawsze** rób je zgodne. Inaczej mylisz siebie i czytelnika.

## Krok 3 — Eksperyment (15 min)

1. **Własny moduł od zera** — uczeń robi to poza katalogiem zadań:
   ```sh
   mkdir ~/moj-projekt && cd ~/moj-projekt
   go mod init github.com/uzytkownik/moj-projekt
   cat go.mod
   ```
   > "Czemu nazwa wygląda jak adres?" → żeby była niepowtarzalna na świecie i żeby dało się ją pobrać. Repozytorium nie musi jeszcze istnieć.
2. **Zależność zewnętrzna:**
   ```go
   package main

   import (
       "fmt"
       "github.com/google/uuid"
   )

   func main() {
       fmt.Println(uuid.New().String())
   }
   ```
   ```sh
   go mod tidy
   go run .
   cat go.mod
   cat go.sum
   ```
   > "Co dopisało `go mod tidy` do `go.mod`?" → sekcję `require` z wersją
   > "Po co `go.sum`?" → sumy kontrolne: gwarancja, że pobrana biblioteka to dokładnie ta, którą sprawdzono. Ochrona przed podmianą.
   > "Oba pliki idą do repozytorium czy tylko `go.mod`?" → **oba**
3. **`go mod tidy` sprząta w obie strony** — uczeń usuwa import `uuid` z kodu i uruchamia `go mod tidy` ponownie:
   > "Co zniknęło z `go.mod`? `tidy` dodaje brakujące i usuwa niepotrzebne."
4. **Gdzie właściwie leżą pobrane biblioteki:**
   ```sh
   go env GOMODCACHE
   ls $(go env GOMODCACHE)/github.com
   ```
   > "Pobrane raz, współdzielone przez wszystkie twoje projekty. Nie ma katalogu z bibliotekami wewnątrz projektu."
5. **Sprawdzanie i aktualizacja:**
   ```sh
   go list -m all              # wszystkie zależności
   go list -m -u all           # które mają nowsze wersje
   go get -u ./...             # aktualizuj
   go mod tidy
   ```
   > "Aktualizować od razu czy ostrożnie? Co może pójść nie tak?"
6. **Struktura typowego projektu** — uczeń ogląda:
   ```
   moj-projekt/
   ├── go.mod
   ├── go.sum
   ├── main.go
   ├── README.md
   └── wewnetrzne/
       ├── konfiguracja/
       └── magazyn/
   ```
   > "Katalog o nazwie `internal` ma specjalne znaczenie: pakiety w środku mogą być importowane **tylko** przez ten projekt. Go pilnuje tego samo."

## Krok 4 — Pogłębienie (10 min)

**Pojęcia — uporządkowanie:**
| Pojęcie | Co to | Przykład |
| --- | --- | --- |
| moduł | cały projekt, jednostka wersjonowania | `github.com/user/projekt` |
| pakiet | jeden katalog z plikami `.go` | `kalkulator`, `fmt` |
| ścieżka importu | nazwa modułu + ścieżka katalogu | `github.com/user/projekt/kalkulator` |
| `go.mod` | nazwa modułu, wersja Go, zależności | — |
| `go.sum` | sumy kontrolne zależności | — |

**Wersjonowanie semantyczne:** `v1.2.3` = zmiany łamiące / nowe funkcje / poprawki. Wersje `v2` i wyższe mają numer **w ścieżce importu**: `github.com/user/projekt/v2`.

**Zasady zdrowego rozsądku przy zależnościach:**
- każda zależność to cudzy kod w twoim programie — i cudze błędy
- do czegoś, co napiszesz w 20 liniach, nie dodawaj biblioteki
- biblioteka standardowa Go jest duża; sprawdź ją, zanim sięgniesz na zewnątrz
- patrz na datę ostatniej zmiany i liczbę otwartych zgłoszeń

**Kiedy dzielić na pakiety?** Nie na początku. Jeden `main.go` jest w porządku, dopóki się nie rozrośnie. Sygnały do podziału: plik ponad ~500 linii, wyraźnie osobna odpowiedzialność, kod przydatny w innym projekcie.

**`go.mod` a wersja kompilatora:** linia `go 1.22` mówi, jakiej **semantyki** oczekuje kod (np. zachowania pętli z 3.3), nie jakiego kompilatora używasz. Nowszy kompilator to uszanuje.

## Pułapki
- **Ścieżka importu ≠ ścieżka na dysku** — importujesz przez nazwę modułu, nie przez `./katalog`. `import "./kalkulator"` **nie działa** w Go z modułami.
- **Cykliczne importy** — pakiet A importuje B, a B importuje A → `import cycle not allowed`. Rozwiązanie: wydzielić wspólną część do trzeciego pakietu.
- **Mała litera = niewidoczne poza pakietem** — działało w jednym pakiecie, teraz naprawdę blokuje.
- **`go get` bez `go mod tidy`** — `go.mod` puchnie od nieużywanych wpisów.
- **Brak `go.sum` w repozytorium** — inni nie mają gwarancji, że pobiorą to samo.
- **Nazwa pakietu inna niż katalog** — kompiluje się, ale przy imporcie trzeba użyć nazwy pakietu, nie katalogu. Mylące bez powodu.
- **`go mod init` w katalogu, który już jest w module** — zagnieżdżone moduły. Rzadko o to chodzi.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`GOPATH` nie jest już potrzebny** (moduły od 1.16). Tutorial każący trzymać kod w `~/go/src` jest przestarzały.
- **`tool` w `go.mod`** (1.24) — deklarowanie narzędzi projektu; zastępuje dawny hack z plikiem `tools.go`.
- **`go mod ignore`** (1.25) — pomijanie katalogów przy dopasowywaniu wzorców.
- **`go mod init` w 1.26+** wpisuje niższą wersję minimalną niż zainstalowany kompilator — celowo, dla zgodności.
- **`go mod tidy` w 1.27** scala zduplikowane bloki `require`.

## Notatki tutora
- **To lekcja "porządkowa", nie konceptualna.** Uczeń pracował dotąd w gotowym module; teraz rozumie, co się działo.
- **Eksperyment 2 (prawdziwa zależność) jest ważny** — pierwszy raz uczeń używa cudzego kodu. To duży krok i warto go docenić.
- Jeśli uczeń chce od razu dzielić wszystko na pakiety — hamuj. Przedwczesny podział jest częstszym problemem niż zbyt duży plik.
- Nie wprowadzaj `go work` (workspace) ani `replace`. Poza kursem.
- Jeśli uczeń pyta o publikowanie własnej biblioteki — to `git tag v0.1.0` i push; ale zostaw to na 12.4.
