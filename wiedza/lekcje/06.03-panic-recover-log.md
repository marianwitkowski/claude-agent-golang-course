# Lekcja 6.3 — `panic`, `recover` i logowanie

## Cel
Po lekcji uczeń:
- Czyta komunikat paniki i znajduje w nim linię, która ją wywołała
- Wie, kiedy `panic` jest uzasadniona, a kiedy trzeba zwrócić błąd
- Rozumie, do czego służy `recover` i dlaczego używa się go rzadko
- Loguje zdarzenia przez `log` i wie o istnieniu `log/slog`

## Krok 1 — Zakotwiczenie (5 min)
**Pytanie wejściowe:**
> "Jedziesz samochodem. Zapala się kontrolka niskiego poziomu paliwa — co robisz? A gdy urwie się koło?"

**Co chcesz usłyszeć:** przy paliwie jadę dalej i szukam stacji (obsługuję problem); przy urwanym kole zatrzymuję się natychmiast, dalsza jazda nie ma sensu.

**Drugie pytanie:**
> "Która z tych sytuacji jest częstsza? Której powinieneś się spodziewać, pisząc program?"

## Krok 2 — Mostek (5-10 min)
**Mostek:**
> "Kontrolka paliwa to `error` z lekcji 6.1 — normalna sytuacja, przewidziana, obsługiwana. Urwane koło to **panika**: dalsze działanie nie ma sensu, program się zatrzymuje. W Go 99% problemów to kontrolka, nie koło."

Uczeń tworzy `kurs/zadania/18-panika/main.go`:

```go
package main

import "fmt"

func main() {
	liczby := []int{1, 2, 3}
	fmt.Println("przed")
	fmt.Println(liczby[10])
	fmt.Println("po")     // nigdy się nie wykona
}
```

Uruchomienie → uczeń wkleja **cały** komunikat:
```
panic: runtime error: index out of range [10] with length 3

goroutine 1 [running]:
main.main()
	/.../18-panika/main.go:9 +0x1d
exit status 2
```

**Pytania:**
- "Która linia komunikatu mówi, **co** się stało?" → pierwsza
- "Która mówi **gdzie**?" → `main.go:9` — plik i numer linii
- "Czy 'po' się wypisało?" → nie, program zakończył się natychmiast
- "Widziałeś już panikę wcześniej w kursie. Gdzie?" → dzielenie przez zero (2.2), zły indeks (4.1), zapis do mapy `nil` (4.3)

## Krok 3 — Eksperyment (15 min)

1. **Własna panika:**
   ```go
   func ustawKonfiguracje(sciezka string) {
       if sciezka == "" {
           panic("brak ścieżki konfiguracji")
       }
   }
   ```
   > "Kiedy wolno tak zrobić? Zastanów się: czy program ma sens bez konfiguracji?"
   **Reguła dla ucznia:** `panic` tylko wtedy, gdy problem oznacza **błąd programisty** (zła instalacja, niemożliwy stan), nie błąd użytkownika czy danych.
2. **Panika a `defer`** — powrót do 5.3:
   ```go
   func zPanika() {
       defer fmt.Println("sprzątam")
       panic("coś padło")
   }
   ```
   > "Czy `defer` się wykonał mimo paniki?" → tak. Dlatego `defer plik.Close()` jest bezpieczny nawet przy awarii.
3. **`recover` — zatrzymanie paniki:**
   ```go
   func bezpiecznie() {
       defer func() {
           if r := recover(); r != nil {
               fmt.Println("złapałem panikę:", r)
           }
       }()
       panic("wybuch")
   }

   func main() {
       bezpiecznie()
       fmt.Println("program żyje dalej")
   }
   ```
   > "Program przeżył. Zwróć uwagę, gdzie stoi `recover` — czemu **musi** być w `defer`?"
   → bo po panice wykonują się tylko odłożone funkcje; zwykły kod za `panic` już nie działa
   > "Spróbuj wywołać `recover()` poza `defer`." → zwróci `nil`, nic nie złapie
4. **Kiedy `recover` ma sens:**
   > "Wyobraź sobie serwer obsługujący 1000 użytkowników. Zapytanie jednego z nich powoduje panikę. Czy wszyscy pozostali powinni stracić połączenie?"
   → nie. Serwery łapią panikę na granicy jednego zapytania.
   **Poza tym przypadkiem `recover` jest w kodzie ucznia zbędny.** Nie używaj go do zwykłej obsługi błędów.
5. **Logowanie** — uczeń dopisuje:
   ```go
   import "log"

   log.Println("start programu")
   log.Printf("wczytano %d rekordów\n", 42)
   ```
   > "Porównaj wynik z `fmt.Println`. Co doszło?" → data i godzina, i wypisywane jest na **wyjście błędów**, nie na standardowe
6. **`log.Fatal` — logowanie i koniec:**
   ```go
   if err != nil {
       log.Fatal("nie mogę wystartować: ", err)
   }
   ```
   > "`Fatal` wypisuje i kończy program przez `os.Exit(1)`. Uwaga: `defer` **się nie wykona**. Gdzie taka funkcja ma sens?"
   → tylko w `main`, przy błędzie startowym. Nigdy w bibliotece ani głęboko w kodzie.

## Krok 4 — Pogłębienie (10 min)

**Tabela decyzyjna — najważniejsza rzecz z tej lekcji:**
| Sytuacja | Co zrobić |
| --- | --- |
| Użytkownik podał złe dane | zwróć `error` |
| Pliku nie ma / brak uprawnień | zwróć `error` |
| Sieć nie odpowiada | zwróć `error` |
| Program dostał niemożliwy stan (błąd w twoim kodzie) | `panic` |
| Brak wymaganej konfiguracji przy starcie | `log.Fatal` w `main` |
| Serwer, jedno zapytanie się wywaliło | `recover` na granicy zapytania |

> "Ile wierszy z tej tabeli to `error`? To dobrze oddaje proporcje w prawdziwym kodzie Go."

**Czytanie stack trace** — uczeń ogląda ślad z kroku 2:
- czytaj **od góry**: najpierw komunikat, potem funkcje od tej, która padła
- linia z twoim plikiem i numerem to zwykle miejsce, gdzie zacząć
- `goroutine 1 [running]` — o goroutine w module 11; na razie: to numer wątku wykonania

**Logowanie strukturalne (`log/slog`)** — nowocześniejsze:
```go
import "log/slog"

slog.Info("zamówienie przyjęte", "id", 42, "klient", "Anna")
```
→ `time=... level=INFO msg="zamówienie przyjęte" id=42 klient=Anna`
> "Czym to lepsze od `log.Printf`?" → dane są w polach, a nie wtopione w zdanie — maszyna potrafi je odfiltrować i policzyć. Przy jednym programie na własny użytek nie ma różnicy; przy setce serwerów jest ogromna.

**`log` vs `fmt`:**
- `fmt.Println` — to, co użytkownik ma **zobaczyć** (wynik programu)
- `log.Println` — to, co ma trafić do **dziennika** (przebieg, diagnostyka)
Uczeń sprawdza rozdzielenie: `go run ./18-panika > wynik.txt` — logi nadal widać na ekranie, bo idą na wyjście błędów.

## Pułapki
- **Używanie `panic` zamiast `error`** — najczęstszy błąd osób przychodzących z języków z wyjątkami. `panic` to nie jest `throw`.
- **`recover` poza `defer`** — zwraca `nil` i nic nie robi. Cicha porażka.
- **`recover` łapiący wszystko** — ukrywa prawdziwe błędy w programie. Panika ma prawo zabić program; to sygnał, że coś jest głęboko nie tak.
- **`log.Fatal` w bibliotece albo w środku logiki** — zabija cudzy program bez pytania i pomija `defer`. Tylko `main`.
- **Panika wewnątrz goroutine kończy **cały** program** — `recover` w `main` jej nie złapie. Wróci w 11.1.
- **`fmt.Println` do diagnostyki** — działa, ale miesza się z wynikiem programu. Diagnostyka to `log`.

## Aktualizacja 2026 (z `AKTUALIZACJE.md`)
- **`log/slog`** (1.21) — logowanie strukturalne w bibliotece standardowej. Nowe programy warto pisać od razu ze `slog`. W kursie: `log` jako podstawa, `slog` jako "gdy program urośnie".
- **Go 1.25 poprawił błąd kompilatora** dotyczący sprawdzania wskaźników `nil` — kod, który wcześniej po cichu robił coś dziwnego, dziś poprawnie panikuje. Praktyczna konsekwencja: pisz `if err != nil { return }` **przed** użyciem wyniku, nigdy po.

## Notatki tutora
- **Główny przekaz lekcji: `panic` prawie nigdy.** Jeśli uczeń wyjdzie z lekcji z wrażeniem, że `panic` to sposób na obsługę błędów — lekcja się nie udała. Tabela decyzyjna z kroku 4 jest ważniejsza niż cała reszta.
- **`recover` pokazuj wyłącznie jako ciekawostkę** z jednym uzasadnionym zastosowaniem (serwer). Uczeń nie powinien go pisać w swoim kodzie.
- Czytanie stack trace to praktyczna umiejętność — jeśli uczeń panikuje na widok czerwonego tekstu, poświęć chwilę na "gdzie w tym szukać swojej linii".
- Nie wprowadzaj `errors.As` z własnym typem błędu — to moduł 7/8.
- Jeśli uczeń pyta o `slog` szerzej (poziomy, handlery, JSON) — powiedz, że to temat na później, i podaj `go doc log/slog`.
